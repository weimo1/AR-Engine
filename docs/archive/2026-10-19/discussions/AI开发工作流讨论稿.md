## 1. 目标与基本原则

AI 承担需求分析、方案设计及开发执行工作。用户通过文档审阅确认需求、产品范围、技术方案和架构；AI 在已确认基线内完成编码、测试、代码审查、Commit、MR、合并和维护，普通实现步骤不逐项要求人工批准。

“全 AI”不等于允许 AI 无条件宣布完成。项目以可追溯的输入、可检查的约束、可复现的证据和受控的变更提供保障，不承诺零缺陷。

1. 需求定义目标，架构定义边界，技术方案定义实现，证据支持完成结论。
2. 每个任务范围有限、可以验收、可以恢复；优先完成能够运行的完整链路。
3. 能自动检查的规则写进工具和 CI；需要判断的规则通过设计与代码审查落实。
4. 实现者不能自行降低验收条件、删除失败检查或修改保护规则来获得通过。
5. 未执行、执行失败、环境不支持和执行通过必须分别记录。
6. 不依赖聊天记录作为唯一项目记忆；决策、任务状态和验证结果进入持久记录。
7. 自动化从最小闭环建设起，按实际问题扩展，不以流程复杂度作为质量指标。

## 2. 产品与技术边界

当前项目是以实时三维渲染为核心的个人渲染引擎，第一版服务毕业设计展示，后续持续发展。

- 已知基线：C++23、Vulkan 1.4；固定工具链与运行库配置。
- 引擎可独立运行；编辑器使用引擎，渲染核心不得依赖编辑器。
- 第一版围绕静态场景、glTF、PBR、方向光、IBL、阴影、HDR、基础编辑、性能统计和保存加载形成闭环。
- 两条资源绑定路径按需求顺序推进：Descriptor Set Bindless 在前，Descriptor Heap 在后；扩展、feature、驱动和 SDK 支持必须实测。
- 游戏玩法、物理、网络、脚本和游戏发布系统不属于当前目标。
- ECS 库已采用 EnTT，见 ADR-0007；具体场景组织、Jobs、RHI 与 Render Graph 等仍需技术方案，不从选库推导完整架构已经批准。

旧依赖建议稿曾在父目录被读取，现已移入项目根目录并标明历史状态。现行选型在项目内 ADR-0007，不依赖旧候选维持有效基线。

## 3. 文档体系与信息权威

以下定义信息职责；小任务允许合并文档，避免重复维护。

| 信息 | 内容 | 更新时机 |
| --- | --- | --- |
| 产品需求与范围 | 目标、第一版边界、长期候选能力 | 产品意图调整时 |
| 总体架构 | 模块、依赖、数据流、线程、所有权、平台边界 | 架构决策变化时 |
| 工程规范 | C++、Shader、接口、错误、日志、测试、依赖与提交规范 | 规范变更时 |
| AI 工作协议 | 入口、上下文加载、权限、状态、失败处理 | 流程变更时 |
| 环境与验证指南 | 固定工具链、构建、运行、测试、测量命令 | 工具与环境变化时 |
| 需求中的行为与验收 | 范围、非目标、边界行为、验收编号，合并在需求或变更说明中 | 功能建立或需求变更时 |
| 技术方案 | 数据结构、接口、生命周期、实现步骤、验证和回退 | 实现前及方案调整时 |
| ADR | 重要选择、备选、理由、影响和重新考虑条件 | 重要技术决策形成时 |
| 任务记录 | 依赖、状态、负责人角色、分支、提交、下一步 | 状态迁移时 |
| 验证与审查记录 | 提交版本、环境、命令、结果、证据和未解决项 | 验证或审查后 |

产品范围以已确认需求为准；技术约束以已接受的架构和 ADR 为准；当前实现事实通过仓库和运行结果确认。代码现状不能自行改写产品意图，文档也不能作为功能已经实现的证据。

发现冲突时：标记冲突 → 判断影响 → 形成修正或变更提案 → 完成相应审查 → 同步文档、代码和验收。不得静默选择有利于通过检查的解释。

需求中的模糊处，由 AI 提出满足现有目标的最小解释并记录。涉及用户可见行为、验收条件、范围或关键技术选择时，形成文档差异交由用户确认；普通局部实现细节可由 AI 自主决定。等待确认期间继续不依赖该决定的工作，不擅自扩大产品范围。

## 4. 角色与权限

角色表示职责，不要求每项职责都部署为常驻 Agent。独立审查宜采用新会话或独立上下文，并直接读取变更与依据。同一模型仍可能具有共同盲点，不能把多次同意当作正确性证明。

| 角色 | 职责 | 限制 |
| --- | --- | --- |
| 协调角色 | 维护任务依赖、选择就绪任务、组织检查与交接 | 不能凭进度压力跳过关卡 |
| 需求与设计角色 | 编写需求与验收说明、架构分析、技术方案和 ADR | 不能擅自扩大已确认产品范围 |
| 实现角色 | 修改代码与相关测试、运行检查、提交变更 | 不能单方面降低验收或解除保护 |
| 审查角色 | 审核方案、差异、证据、风险与需求符合性 | 不能只依据实现者总结批准 |
| 验证执行器 | 在指定环境运行检查，保存原始结果 | 检查失败不得转换为通过 |
| 合并执行器 | 检查合并条件，执行合并和集成验证 | 不绕过保护规则，不自行解释豁免 |

流程、CI、基准图、性能阈值、需求和架构规则的变更属于治理变更。它们由 AI 提出并经独立审查；其中涉及已确认需求、产品范围、技术方案、架构或降低质量关卡的变化，还必须取得用户对文档变更的确认。普通检查器修复可以由 AI 自主处理，但不得由实现任务自行放宽规则以消除自身失败。

紧急修复仍需要针对性验证和审查。若要修改已有规则，应使用独立可审查的变更，说明旧规则的问题和替代保障。

权限隔离应在平台支持范围内由凭据、分支保护和 CI 权限落实。若实现和审查共用同一个仓库身份，必须明确这种独立性仅是流程上的；不得伪造不同身份或宣称已满足平台的独立批准要求。平台不支持当前设计时，应先完成能力适配，不绕过保护。

## 5. 项目启动阶段

功能批量开发前，AI 完成以下初始化：

1. 盘点已有需求、文件、工具、硬件和远程仓库；未知项显式记录。
2. 明确第一版里程碑与最低验收，区分稳定展示目标和实验目标。
3. 建立总体架构初稿，优先确定模块依赖、主循环、资源归属和 CPU/GPU 生命周期。
4. 对高风险技术做最小实验，记录实际设备与支持情况；实验结论进入方案，试验代码不自动成为正式模块。
5. 固定可复现的工具链、依赖版本、配置和基础命令。
6. 建立最小可构建运行程序、日志、退出状态、基础自动检查和 MR 流程。
7. 从首条运行链路开始提供自动场景加载、固定相机、截图和退出接口，再逐步扩展。

自动化观察接口在原需求中属于后续能力。由于本项目要求全 AI 开发，本工作流建议将其最小子集前移；这是流程配套建议，需在定稿时与需求安排同步。

初始化阶段允许基础设施尚不完整，但必须列出临时检查方式、缺失项和完成条件；不能把过渡状态描述为完整保障。

## 6. 单项功能的标准流程

### 6.1 需求就绪

需求或变更说明中的行为与验收部分必须包含，不单独建立需求与验收说明文档：

- 功能编号、需求来源、目标、使用流程与非目标。
- 正常行为、边界行为和失败行为。
- 可观察的验收条件及编号。
- 运行环境、数据或资产要求，以及性能约束是否适用。
- 依赖、未知项及需要验证的假设。

AI 需求审查检查：不越界、关键行为无歧义、验收能执行。新增需求或修改既有行为与验收时，由用户确认相应规格文档后进入就绪状态。已有确认文档完整覆盖的小缺陷可以使用问题复现和预期行为作为简化规格，不重复请求同一决定。

### 6.2 方案就绪

技术方案回答：涉及哪些模块；接口与数据如何变化；谁拥有和释放资源；线程与 GPU 同步如何处理；失败如何报告；如何验证、迁移和回退。

重大方案列出备选与取舍。新增依赖、跨模块接口、存储格式和性能关键设计需要架构影响审查。没有影响的部分明确写“不涉及”，不机械填写长文。

接口契约至少明确适用的前置条件、结果、错误、所有权、生命周期和线程限制。避免仅列函数签名。

技术未知先做有退出条件的实验。不能为了赶进度将未验证假设写成事实。

AI 完成技术方案及架构影响审查后，提交具体方案文档供用户审阅确认。已有确认方案完整覆盖的任务不重复审批；改变技术路线、跨模块契约、生命周期策略或其他基线约束时，提交文档差异重新确认。用户审阅不能替代 AI 技术审查和实际验证。

### 6.3 任务拆分与实现

每个任务绑定需求与验收说明、方案版本、允许修改的范围、验收和相关检查。规模以能独立理解和验证为准，不设置机械的代码行数配额。

任务开始时确认仓库状态和基线，使用任务分支；存在其他未提交工作时，保护其内容，不覆盖、不擅自清理。

实现中发现方案不成立时，先更新影响分析和方案；影响架构或契约的变化重新审查。允许普通局部实现调整，不为每个小选择建立审批。

并行任务需要已明确的接口与文件归属。重叠修改由协调角色串行安排或显式解决，禁止以最后写入覆盖他人结果。

### 6.4 本地验证与提交

先运行与变更相关的检查，再运行本阶段要求的回归。失败必须修复或定位为明确阻塞，不能靠反复重跑挑选一次通过。

完成有意义的实现步骤后 Commit。提交描述问题或行为变化，关联任务；不得混入无关大规模格式化、缓存、私密信息或生成物。必要的开发中间提交可以保留在分支，合并前按约定整理。

### 6.5 MR、CI 与独立审查

MR 至少包含：功能和任务链接、实现摘要、架构或接口影响、验证结果、已知限制、回退方式。

CI 对指定提交执行必需检查。审查者直接检查规格、方案、差异和证据，重点检查正确性、GPU 生命周期、同步、错误路径、测试有效性与范围偏移。

问题按阻塞、必须修复和建议分类；建议默认不阻塞。审查结论明确对应提交版本，不使用“看起来可以”代替结论。

新提交使受影响的验证和审查失效，重新执行相关检查；无关证据可保留，但必须说明适用范围。合并执行器核验 MR 最新提交及目标分支状态，避免批准的版本与实际合并版本不一致。

### 6.6 合并与关闭

仅当必需检查通过、阻塞问题清零、审查有效且满足仓库保护时允许自动合并。目标分支变化可能影响结论时，重新集成验证或使用平台合并队列。

合并后验证实际主分支版本。失败时暂停依赖该结果的任务，优先回退或提交修复；未恢复之前不得报告交付完成。

功能关闭需要验收覆盖、文档同步、已知限制记录和实际集成证据。MR 合并本身不等于功能完成。

## 7. 任务状态与失败恢复

建议状态：待澄清 → 待需求文档确认 → 规格就绪 → 待方案文档确认 → 方案就绪 → 实现中 → 待验证 → 待评审 → 可合并 → 已合并待集成验证 → 已完成。已有基线完整覆盖时，引用有效确认记录进入对应就绪状态，不重复审批。

每次迁移由对应产出和检查结果支持。另设“阻塞”“已取消”，阻塞记录前序状态、原因、解除条件和可继续的独立任务。不得把阻塞归入完成。

同一失败连续出现且没有新假设或新证据时停止重复尝试。建议初始策略为：连续两次同类修复无效后进入根因分析；外部服务重试次数按服务性质配置，禁止无限循环。

超时、崩溃或上下文中断后：读取任务和仓库状态 → 核对实际提交及未提交改动 → 检查已有证据是否适用 → 从最后有效状态恢复。不能直接信任旧会话的完成声明。

外部凭据、设备或服务缺失时，记录具体缺口和解除条件。AI 可以自动报告需要外部输入，不能伪造输入，也不能把等待时间视作授权。

## 8. 渲染引擎的验证体系

| 层面 | 验证对象 | 证据 |
| --- | --- | --- |
| 静态与构建 | 固定标准、配置、依赖、编译告警、模块边界 | 构建与检查日志 |
| CPU 正确性 | 数学、句柄、序列化、加载失败、场景操作 | 单元、性质或集成测试结果 |
| Vulkan 正确性 | feature 检查、同步、描述符、资源访问与释放 | 设备信息、Validation 输出、运行日志 |
| 图像 | 固定场景下的材质、光照、颜色、阴影和调试视图 | 截图、差异图、容差和结论 |
| 稳定性 | resize、最小化恢复、场景切换、重复加载与退出 | 自动操作记录、崩溃与资源诊断 |
| 性能 | CPU/GPU 分阶段耗时、内存、卡顿 | 固定负载下的样本、统计与基线 |
| 编辑器 | 选择、变换、参数调节、保存和重新打开 | 操作脚本、日志与结果检查 |

按变更风险选择检查，不要求每次修改执行全部 GPU 基准。纯文档变更与 GPU 同步修改适用不同检查集合；检查集合由规则决定，实现者不得任意删减。

核心 GPU 改动的必需硬件检查不能用 CPU mock 或软件实现结果完全替代。普通 CI 没有 GPU 时，应进入具备指定设备的验证队列。

每份重要运行证据记录：提交版本、构建配置、工具链、GPU、驱动、SDK、实际启用的 feature、场景与资产版本、相机、分辨率、参数、随机种子和适用的预热/采样设置。记录原始结果、命令与退出状态。

截图基线需有来源、预期和审查记录；不能因为新图产生了差异就自动接受。为跨设备误差或随机渲染设定合理容差，禁止随失败任意放宽。

性能比较固定环境，分别考虑平均值、分位数与异常卡顿；阈值通过基线测量确定。噪声导致的重测需说明原因并保留失败结果。

### 双绑定路径的特殊要求

- 先验证 Descriptor Set Bindless，再独立验证 Descriptor Heap 所需环境和原型。
- 在相同场景、资产、材质、相机和设置下比较图像、行为及性能。
- 不支持某路径时输出明确能力诊断，标记未支持/未验证，不静默切换后声称该路径通过。
- 毕设稳定版本可依据需求固定已验证路径；另一条路径仍作为未完成能力跟踪，不能因此宣布双路径目标完成。

## 9. 工程约束如何落地

每条重要规则需注明适用范围、检查方式和失败动作。例如：

| 规则 | 执行方式 | 失败动作 |
| --- | --- | --- |
| Runtime 不依赖 Editor | 构建目标依赖检查，补充 include 审查 | 阻止合并 |
| 固定 C++23 与运行库配置 | 构建配置与 CI 验证 | 阻止合并 |
| GPU 对象生命周期明确 | 契约审查、验证层和压力场景 | 阻止相关功能交付 |
| 新接口需明确错误与所有权 | 方案及代码审查 | 返回修正 |
| 不以关闭检查解决失败 | 治理变更审查、保护配置 | 阻止合并并记录原因 |

具体命名、格式化、异常策略、断言、日志等级、Shader 规范、第三方库封装程度等需在工程规范中另行确定。工具不能完整检查的内容应如实说明，不声称已完全自动保障。

架构也需要允许受控演进：先记录问题与证据，再提出 ADR 和迁移方案，完成审查及回归后更新约束，避免旧架构永久阻止合理改进。

## 10. 追溯、交接与版本

保持关联：需求编号 → 需求与验收说明 → 技术方案/ADR → 任务 → Commit/MR → 验证证据 → 发布版本。

任务交接至少记录：当前状态、分支与提交、未提交改动、完成与未完成项、有效检查、已知失败、下一步和阻塞。AI 入口文档保持简短，指向权威资料，不复制所有内容。

毕业设计版本单独建立不可变标签及发布说明，保存运行包、工具链/依赖记录、场景资产版本、截图和性能证据。后续开发继续在主线上进行，不覆盖既有展示版本。

大文件与证据的存储、保留期和资产许可记录另行确定。不能假设外部素材可以任意分发。

## 11. 建设顺序

1. 根据已确认的 OpenSpec 与 Harness 方向，补齐执行细节、角色权限和第一版里程碑。

总体架构与 ADR 由设计文档引用，不在每个变更目录中重复复制。原始日志、截图和性能样本存放在证据存储中，文档保留索引和内容标识，避免将大量二进制结果混入代码提交。

## 15. OpenSpec 在本项目中的执行方式

标准链路为：

```text
创建变更与 proposal
→ 在需求/变更说明中明确行为与验收，按需建立工具 specs 映射
→ 技术方案 design 与验证计划 test-plan
→ 独立 AI 设计审查
→ 用户确认新增或变更的需求、技术方案及架构文档
→ 任务拆分与就绪检查
→ 实现、验证、Commit
→ MR、CI 与独立 AI 代码审查
→ 自动合并
→ 合并后集成验收
→ 同步当前规格并归档变更
```

OpenSpec 的默认迭代能力保留；实现中可以修正规格与设计，但涉及验收、契约或架构的变化，必须更新相应产物并使相关审查失效。不能用“允许修改文档”替代变更审查。

归档不会使未通过验收的功能变成已交付。当前规格更新必须与已验收代码对应；归档产生的规格、状态和文件移动也通过受控分支提交。初期可在集成验收后创建关联收尾 MR，收尾合并后才将任务关闭。收尾变更不得再次触发新的归档任务形成循环。

变更分为四种路径，由协调角色分类、审查角色确认：

| 类型 | 最低要求 |
| --- | --- |
| 普通功能 | 需求/变更说明中的行为与验收、设计、测试计划、任务、两阶段审查与集成验收 |
| 小缺陷 | 复现、预期行为、简短方案、适用回归和代码审查；无契约变化可合并文档 |
| 技术实验 | 问题、假设、环境、退出条件和结论；不得以实验通过代替正式交付 |
| 治理变更 | 明确规则变化、原因、影响和替代保障，接受独立审查；涉及基线或降低质量关卡时由用户确认，不由受益实现任务自行豁免 |

纯文档、格式调整等低风险变更按影响精简产物和检查，不机械运行 GPU 测试。发现实际影响超出分类时升级流程。

## 16. TDD 与验证计划的具体规则

每个验收项分配稳定编号。`test-plan.md` 将其映射到测试或检查入口，并注明环境、输入、预期、通过条件及原始证据位置。

| 变更内容 | 默认策略 |
| --- | --- |
| 句柄、引用关系、序列化、场景层级等确定性逻辑 | 优先 TDD |
| 可稳定复现的缺陷 | 先补充能暴露原缺陷的回归测试 |
| GPU 生命周期、同步与绑定 | 可隔离逻辑测试，加真实设备集成与验证层检查 |
| 渲染算法与画面效果 | 适用的数值检查、固定场景、图像差异与专项审查 |
| 性能优化 | 先采集可复现基线，再修改并进行同条件比较 |
| 未确认技术路径 | 先实验，再决定正式方案和测试策略 |
| 无行为变化的低风险文档或格式调整 | 相关静态检查与审查，不强制新增测试 |

适用 TDD 的任务按以下步骤执行：

1. 根据规格写最小有效测试，测试描述预期行为，不重复实现细节。
2. 在实现前执行并观察失败，确认失败原因对应缺失行为。
3. 实现满足行为的代码，执行测试得到通过结果。
4. 保持行为不变进行必要重构，再运行相关回归。
5. 记录 RED 与 GREEN 对应的源码版本或补丁标识、测试标识、命令及原始结果。无需为每次 RED 创建独立 Commit，但必须能够重建对应状态。

环境错误、测试发现失败、依赖缺失和无关编译错误不能作为有效 RED。无法在实现前执行的测试如实标记，不补写虚假的 TDD 记录。

验收要求属于独立输入；实现者同时编写测试时，审查者必须检查断言与验收的关系。需要时使用已知错误样例或针对性负向检查验证测试能识别错误，不为所有代码机械增加此类测试。

不使用统一覆盖率阈值替代正确性判断，也不为了增加测试数量测试无意义细节。未采用 TDD 的功能仍必须有明确验证策略。

## 17. Harness 的最小接口与通过条件

以下是待实现的语义接口，不是当前可调用的命令。实际命令格式、脚本语言和配置格式由落地方案确定。

| 接口 | 必须完成的工作 |
| --- | --- |
| 任务开始/恢复 | 校验任务、仓库状态、基线、依赖、所需上下文与环境 |
| 选择检查 | 根据受版本管理的影响规则生成必需检查集合 |
| 执行验证 | 执行检查，保存原始结果和环境，返回明确状态 |
| 请求设计/代码审查 | 提供依据、差异及版本，保存独立结论和问题 |
| 检查合并资格 | 核验最新提交、目标分支、必需证据、审查与平台保护 |
| 集成验收/关闭 | 验证合并后版本、同步规格、完成收尾或记录失败 |

验证状态至少区分 `passed`、`failed`、`blocked`、`not_run` 和 `not_applicable`。不适用必须有规则依据；环境不支持但属于必需检查时为阻塞，不能算不适用。

合并条件至少包括：

- MR 最新提交的必需检查全部通过。
- 所需设计和代码审查有效，阻塞及必须修复问题清零。
- 涉及需求、范围、技术方案或架构基线变化时，具备适用于当前文档内容的用户确认记录。
- 规格、设计和代码之间无未处理冲突。
- 目标分支变化未使证据失效，满足仓库保护和权限约束。

审查记录绑定代码提交、相关规格/设计的内容标识和适用基线。后续变更是否使其失效由影响规则决定，不能简单检查 review 文件存在或出现“通过”字样。后续审查记录提交造成自身文件变化时，应明确其不改变被审对象，避免无限要求对审查记录本身重新审查。

涉及 CI、Harness 或保护规则的变更，使用目标分支上的已接受规则或独立可信检查执行器核验，不能只依赖变更分支自行输出通过结果。证据不得包含凭据；实现任务不应获得用于解除保护或伪造检查结论的权限。

## 20. 用户与 AI 的决策边界

本节明确：用户通过文档掌握需求、产品范围、技术方案和架构决定权；AI 执行这些决定并提供检查证据。早期“全部由 AI 做”的表述不再解释为 AI 可以自行批准这些基线。

| 事项 | AI 负责 | 用户参与 |
| --- | --- | --- |
| 需求、范围及验收 | 分析、整理选项、编写规格与影响说明 | 审阅确认文档及其变化 |
| 技术路线、总体架构、关键技术方案 | 调研、必要实验、方案与 ADR、独立技术审查 | 审阅确认文档及其变化 |
| 已确认方案内的任务拆分与局部实现 | 自主实施并接受 AI 审查 | 无需逐项确认 |
| 构建、测试、代码审查、Commit、MR 和合并 | 满足关卡后自动执行 | 默认不设置逐次人工审批 |
| 改变基线或降低质量关卡 | 编写变更理由、影响与替代保障 | 确认具体文档差异 |

文档记录至少区分：草案、待用户确认、已确认、已取代。确认绑定文档版本或内容标识，并保存确认来源；用户可以在聊天中明确确认，由 AI 记录，无需预先建设专门审批界面。不能把用户沉默、阅读、讨论或对局部条款的同意当作整份文档批准。

文档更新后，根据差异判断原确认是否仍适用。错别字、链接等无语义修正无需重新确认；影响约束、验收或设计选择时，使相关确认失效。被取代的版本保留追溯，新版本未确认前不得按其实施受影响部分。

AI 提请审阅前应完成其能够独立完成的调研、文档和审查，提供具体方案与差异，避免只提交空泛选择题。必要的低风险可逆技术实验可在已确认范围内开展，结果不自动成为正式架构。

本文件仅将本轮明确的权限边界和此前选定的框架方向记录为已确认，不据此宣称所有工作流细节、架构、需求条目或技术方案都已经获批。后续继续按主题讨论并更新文档。

## 21. 文档体系与模板讨论入口

文档分类、权威来源、确认状态、版本绑定、重新确认条件和模板目录详见 [文档体系与确认机制](../../../workflow/文档体系与确认机制.md)。其具体条款及模板目前为草案，供逐项讨论，不表示已经部署检查器或启用 OpenSpec schema。
