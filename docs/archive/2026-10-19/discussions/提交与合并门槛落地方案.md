## 1. 三层门槛

| 门槛 | 触发点 | 必需内容 | 失败行为 |
| --- | --- | --- | --- |
| Commit gate | 每次普通提交前 | 暂存范围/冲突标记/格式检查、适用快速检查、实现者代码自检 | 阻止普通提交；修改后重验 |
| PR gate | 每次 PR 更新，及目标变化需要重验时 | 受影响构建与测试、Shader 检查、独立 AI Review、适用 GPU 验证、证据完整性 | 不具备合并资格 |
| Integration gate | 实际合并后提交 | 适用主分支构建与集成冒烟 | 保持未完成，修复或恢复 |

代码自检与独立 Review 分开：每个 Commit 都自检；独立审查覆盖最终待合并变更及新增提交的实际影响。第一版不要求每个本地中间提交启动完整独立审查，但所有代码进入主分支前必须有有效独立审查。审查不能只验证是否存在一个“通过”文件。

本稿收紧交付草案的中间提交说明：开发中间提交也必须通过适用 Commit gate；未完成可以表示功能尚未完整，但不能自动豁免已有格式/快速检查。若确需保存未过门槛的实验状态，应另设计明确的 checkpoint 记录，不用 --no-verify 偷渡为普通合格提交。

## 2. Commit gate 的具体范围

针对即将提交的暂存树和必要受控依赖执行检查，不把含未暂存修复的整个工作目录测试结果当作暂存代码通过。检查输入包含父提交、暂存树内容、适用规则/工具配置；输入变化则原通过记录失效。

- 通用：任务范围、冲突标记、禁止收录的文件与凭据模式、适用格式与提交说明格式。
- 文档：受影响链接、可解析示例与必要一致性，不要求跑 C++/GPU。
- C++：代码自检、受影响目标构建和适用快速 CPU 测试；公共/构建配置变更相应扩大范围。
- Shader：受影响变体编译/验证与接口检查；GPU 冒烟放在相应 PR gate，不默认每次提交全场景渲染。

提交前自检关注范围、契约、所有权、错误路径及测试预期，结果可以简短，但如实说明发现与检查范围。语义 Review 无法用格式器替代，AI 自填自检字段本身不构成独立审查。

## 3. 本地入口与远程复验

建议实现受版本控制的统一检查入口，由 Harness 在提交前强制调用，pre-commit/commit-msg hook 负责接入 Git 并给出及时失败。精确脚本名、参数与实现语言在基础建设方案确定，本文不伪装为已有命令。

[Git hook 文档](https://git-scm.com/docs/githooks) 明确 pre-commit 可以被 --no-verify 绕过；hook 安装与 core.hooksPath 也属于本地配置，因此不能把 hook 单独当成无法绕过的安全边界。AI 执行规则禁止主动绕过；服务端在主分支前重新执行适用检查。

本地与 CI 共用规则、工具版本及检查实现，避免维护两套验收含义。AI 可以申请扩大合理检查范围，不能通过篡改分类器把 C++/Shader 修改伪装成 docs-only 来跳过检查。

## 4. GitHub Actions 建议

建议若选 GitHub，用 Actions 调度构建/测试与证据上传，用保护规则/Ruleset 强制执行合并条件。Actions 不是测试框架；CPU 测试仍由具体测试程序执行，CTest 调度，GPU 程序执行受控场景。

官方 [runner 镜像清单](https://github.com/actions/runner-images) 当前提供 windows-2025-vs2026，[镜像内容](https://github.com/actions/runner-images/blob/main/images/windows/Windows2025-VS2026-Readme.md) 可供核查。建议显式使用对应镜像标签，并预检实际 VS/工具集/SDK；标签内容会更新，不能认为它固定为本机 18.7.1/14.51.36231。版本不符时失败并明确调整方案，不能默默编译另一组合。

建议检查职责与名称（待实现）：

| 名称 | 职责 |
| --- | --- |
| policy-check | 文件范围、格式、配置与必要文档检查 |
| windows-build-test | VS 2026 构建、适用 Debug/优化配置与 CPU 测试 |
| shader-check | 合法变体、编译/验证及接口核验 |
| gpu-validation | 适用真实 GPU 数值/图像冒烟，或有依据的不适用结论 |
| ai-review | 独立审查者对版本与目标基线的有效结论 |
| merge-gate | 汇总本次实际必需集合，仅在满足所有要求时成功 |

PR 的新增提交和适用目标变化重新判断；合并队列如启用，补齐对应事件与检查。普通 push 不要求替代 PR 合并结果检查，push main 用于合并后验证。

## 5. GPU 与 Review 的执行边界

普通 Windows runner 的 VS 标签不证明具备项目所需 Vulkan 设备、驱动与扩展。GPU 检查先查询实际能力，再选择隔离的自托管 GPU runner 或受控本地 Harness，并由受信验证入口回传当前源码与环境的检查结果。截图文件存在或用户贴一条“通过”不能代替受信结果。

实际 GPU 必需却不可用时 gate 保持未满足；不能用无条件 skip、软件实现或较低能力路径冒充真实 GPU 检查。能力依赖的 Descriptor Heap 检查单独记录适用范围，不把未实现/不支持写成全路径通过。

自托管机器执行代码须限定来源、资源和权限，不能默认把个人开发机暴露给任意外部 PR。[GitHub runner 说明](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/add-runners) 指出公开仓库 fork PR 的代码执行风险。具体隔离与触发策略随实际仓库可见性设计。

独立 AI Review 需要真实模型执行环境及版本绑定结果。可以由独立上下文经受信服务回传，也可以由合适机器人身份提交 Review；选择哪种取决于可用账户/平台权限。不得假定一个 workflow YAML 自动提供独立模型或作者可自批准，也不得在 PR 描述中填字段就生成成功检查。

用户提供 Open Code Review 后，已完成 [候选工具评估](../../../research/OpenCodeReview适用性评估.md)。建议作为 PR 独立审查执行器候选，由 Harness 核对其结构化完整性与问题处理状态；退出码 0 不等于无问题，默认文件筛选/通用规则需适配 C++/GLSL/测试。尚未安装或确定采用，不改变现有合并条件。

## 6. 真正强制执行的条件

GitHub [分支保护说明](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) 支持 required status checks 与审查要求；是否可用需核对仓库可见性、账户套餐及权限。

落地时配置主分支只能经 PR、必需检查、有效审查以及适用的更新策略；禁止任务执行身份绕过。按平台能力限制检查结果来源；修改 workflow/gate、规则、基准或保护配置应经适用的独立治理审查，不能让实现者通过同一 PR 放宽自身门槛。

保护分支不等于治理管理员永远无法变更规则。应区分实现、审查结果发布与规则管理权限，限制常规 AI 凭据；若这些身份尚未隔离，必须报告约束尚未达到的范围，不能宣称绝对不可绕过。

merge-gate 必须读取本次必需集合和实际结论。GitHub 可接受某些 skipped/neutral 状态作为必需状态满足，因此不得只检查“工作流是绿色”：检查器失败、取消、超时、该执行却 skipped、无测试或缺少独立审查时均不能由汇总任务放行。不适用判定要有检查过的影响依据。

## 7. 实施验收：证明它会拦截

基础设施完成前必须执行负向验证，而不只保存 YAML/脚本：

1. 受控暂存格式错误、坏测试或编译错误，Commit gate 返回失败；修复后成功，验证未暂存修复不能掩盖暂存错误。
2. 测试失败、检查取消、缺少所需 GPU、独立审查未完成时，PR 无法合并。
3. 推送新代码后旧检查/Review 按实际影响失效；目标分支变化后集成对象正确。
4. 尝试普通身份直推主分支或绕过本地 hook，远程仍阻止不合格代码进入主分支；实验仅在授权测试仓库执行。
5. 检查规则自身被改为放行时，治理/保护机制能识别，记录剩余权限限制。
6. 合并后故意触发隔离场景的集成失败，状态不关闭并能按方案恢复。

当前无 Git 仓库、远程、测试程序与部署权限配置，以上均未执行。实施顺序：确定仓库/身份与工具链 → 统一检查入口与 hooks → 构建/CPU/Shader 检查 → Actions 与保护 → GPU/独立 Review 接入 → 正反向验收。缺失的必需能力应明确阻止相应合并阶段，不能先启用“全绿占位”代替。
