## 1. CPU 数学与配置

采用 GLM，集中数学入口与配置。按 Flower [math.h](<F:/cpp project/flower/source/engine/utils/math.h:3>) 的语义使用弧度与 Vulkan 0—1 深度约定；相关编译单元不得各自改变 GLM 手性、对齐或四元数存储配置。

Flower 定义 GLM_FORCE_RADIANS、GLM_FORCE_DEPTH_ZERO_TO_ONE、GLM_ENABLE_EXPERIMENTAL。基础建设时按固定 GLM 版本核验宏和扩展需求；GTX 实验扩展按实际需要引入，不默认启用整套。不能只依赖 namespace 别名保证首次 include 时的配置一致。

CPU 数学表示与 GPU 传输契约分别处理；GLM vec3、矩阵或四元数不能因名字与 GLSL 相近就直接跳过布局验证。

不把任意相机当前朝向当作世界“前方”；模型局部轴由资产契约明确。旋转存储与 glTF 四元数的字段顺序在导入/序列化方案中显式核对，不通过原始 GLM 内存猜测。Flower Transform 中的 Euler 存储及 const getter 类型不一致不作为本项目接口模板。

颜色转换矩阵与几何变换分开命名；Flower 中颜色函数有 color × matrix 写法，其系数按对应乘法组织，不能为了统一书写顺序直接颠倒运算而不转置/重推系数。

## 3. 主视图投影与深度

- 使用有限近远平面的 RH、ZO 透视投影，按 Flower 交换投影构造的 near/far 参数实现 Reverse-Z；对外参数仍是物理近远距离，满足 0 < near < far。
- 近处映射为深度 1，远处为 0，viewport 深度范围保持 0—1。
- 主视图深度初始使用 D32_SFLOAT，清除值 0；静态网格主视图参考 GREATER_OR_EQUAL。其他 Pass 的 EQUAL/严格 GREATER、写入和偏置按各自用途声明，不统一硬改为同一比较。
- 相机初始参考值：FOV-Y 45°、near 0.001 m、far 10000 m，来源为 Flower [相机默认值](<F:/cpp project/flower/source/engine/utils/camera_interface.h:63>)；它们是可配置初值，不是所有场景必须固定的范围。
- 依据实际投影参数进行深度重建，有限平面的线性距离公式为 near × far / (deviceDepth × (far − near) + near)。无限远、正交与阴影投影如引入，单独定义公式，不能套用此式。

证据：[投影交换](<F:/cpp project/flower/source/editor/widgets/viewport.cpp:549>)、[D32 格式](<F:/cpp project/flower/source/engine/renderer/scene_textures.h:90>)、[清零](<F:/cpp project/flower/source/engine/renderer/scene_textures.cpp:125>)、[静态网格比较](<F:/cpp project/flower/source/engine/renderer/pass/staticmesh_pass.cpp:152>)、[重建公式](<F:/cpp project/flower/install/shader/common_shader.glsl:170>)。

## 4. Y 翻转、屏幕 UV 与正面

主视图按 Flower [viewport 设置](<F:/cpp project/flower/source/engine/graphics/graphics.h:139>)：y = height、viewport.height = −height，投影不再重复翻转 Y。屏幕 UV 左上为原点，转换到 NDC 为 (2u−1, 1−2v)，见 [位置重建](<F:/cpp project/flower/install/shader/common_shader.glsl:151>)。

Flower [光栅默认状态](<F:/cpp project/flower/source/engine/graphics/base.h:434>) 为 CLOCKWISE，但静态网格实际关闭剔除。正面/剔除行为需结合 viewport、资产绕序和镜像变换验证；不得凭默认值推断所有资源都按 CW 导入。第三方 Gizmo、UI、立方体捕获等边界采用各自显式适配，不能随处添加 Y 翻转修画面。

## 5. 颜色与输出

Flower [common_header.h](<F:/cpp project/flower/install/shader/common_header.h:4>) 默认 AP1_COLOR_SPACE = 0。本项目沿用其默认方向：场景光照在线性 sRGB/Rec.709 色域计算，HDR 中间颜色参考 RGBA16F；不是默认所有 Pass 都在 ACEScg 工作。

- Base Color 与 Emissive 颜色贴图使用适当 sRGB 采样解释；Normal、Metallic、Roughness、AO 等数据贴图按线性数据解释。因子、UI 选色与外部图片入口明确各自编码，不能按字段名重复解码。
- 色调映射阶段转换到 AP1，再转换回线性显示色域，最后进行 sRGB 编码。Flower 默认选择其 FilmACES 分支；沿用这一默认方向，不因此承诺其自定义曲线等同完整标准 ACES 显示变换。
- SDR 输出参考 UNORM 缓冲与显式 sRGB 编码的组合。未来若改为 sRGB attachment 的自动编码路径，应移除重复编码并验证 UI 合成；surface colorSpace 不能单独说明像素已被正确编码。
- 渲染中的 HDR 浮点颜色不等于已经支持 HDR 显示器输出；本决定不新增 HDR10 产品能力。

证据：[贴图导入](<F:/cpp project/flower/source/engine/asset/assimp_import.cpp:195>)、[HDR 格式](<F:/cpp project/flower/source/engine/renderer/scene_textures.h:85>)、[默认 FilmACES](<F:/cpp project/flower/source/engine/scene/component/postprocess_component.cpp:188>)、[色调映射与编码](<F:/cpp project/flower/install/shader/post_tonemapper.glsl:58>)、[SDR surface 选择](<F:/cpp project/flower/source/engine/graphics/swapchain.cpp:106>)。

Flower [encodeSRGB](<F:/cpp project/flower/install/shader/common_tonemapper.glsl:177>) 注释提及 Rec.709，但实现为带 0.0031308 分段的 sRGB 编码公式。采用实际公式语义，不能沿用错误注释解释传递函数。色域、线性/非线性编码与浮点存储必须分别表述。

## 7. 其他引擎的数学实现与选择建议

本节为用户随后要求比较其他引擎的调研和建议，不自动改变前述已记录约定。来源为 2026-10-18 读取的官方仓库 main/master 页面；实施时应固定版本。

| 项目 | 本轮直接核实的实现 | 参考边界 |
| --- | --- | --- |
| Filament | [自有 math/mat4.h](https://github.com/google/filament/blob/main/libs/math/include/math/mat4.h) 定义 TMat44，并提供投影、lookAt 和四元数相关操作 | 可以研究接口与测试思路；没有必要为本项目移植其数学库 |
| Godot | [core/math/vector3.h](https://github.com/godotengine/godot/blob/master/core/math/vector3.h) 定义其 Vector3 类型与运算 | 表明引擎可以维护自己的数学体系，不证明本项目也需要承担该维护范围 |
| Diligent Engine | [BasicMath.hpp](https://github.com/DiligentGraphics/DiligentCore/blob/master/Common/interface/BasicMath.hpp) 定义自己的向量、矩阵、四元数模板 | 可参考清晰的基础类型；不推断整个引擎完全不使用其他数学依赖 |
| bgfx 官方示例 | [01-cubes](https://github.com/bkaradzic/bgfx/blob/master/examples/01-cubes/cubes.cpp) 使用 bx::Vec3、bx::mtxLookAt 与 bx::mtxProj | bgfx 接口可接收矩阵数据，示例使用 bx 不意味着调用方必须统一使用 bx |
| Flower | 本文已核查其使用 GLM | 与当前 GLSL 路线和参考实现一致 |

GLM [官方说明](https://github.com/g-truc/glm) 将其定位为基于 GLSL 规范的 header-only C++ 数学库，并提供变换和四元数等扩展。另一个候选 [DirectXMath](https://github.com/microsoft/DirectXMath) 为面向游戏/图形的内联 SIMD 线性代数库；名称不代表只能配 Direct3D，但类型、调用约定与当前 GLSL/Flower 路线需适配。

本项目判断：继续选 GLM，优先减少自行实现基础数学和维护第二套基础类型的成本。没有进行同负载基准，不能声称 GLM、DirectXMath 或其他实现谁一定更快；性能瓶颈出现后按热点测量决定是否增加批处理/SIMD 专用路径。

建议补强方式（尚待相应技术方案落实）：

- 基础向量/矩阵/四元数使用 GLM，集中实现有项目语义的相机投影、深度重建及坐标转换函数；不为每个 GLM 运算再建一层同名转发。
- 相机函数显式表达 RH/ZO/Reverse-Z 语义，验证近远参数交换；函数名是接口设计建议，不要求调用方散布“交换参数”的技巧。
- 旋转数据建议优先四元数，编辑器 Euler 作为交互表示；这与 Flower 的 Euler 字段存储不同，列为待确认建议，资产导入、序列化和插值方案同时明确。
- Flower 的 near=0.001、far=10000 保留为已记录的参考初值，但建议按项目场景尺度复核后确定默认相机预设，避免把参考值当成精度最优结论；本节不直接替换它们。
- 数学库选择不决定颜色管理。沿用本规范的线性 sRGB、HDR 中间结果和显式输出编码，输出正确性需要数值与图像证据；不因引擎有自研库就引入完整 ACEScg 管线。

未改变 GLM ADR，未安装其他数学库，未运行性能或渲染对比。
