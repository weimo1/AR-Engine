## 1. 分支与工作区

建议采用单一稳定主分支 main，加短期任务分支，不先引入长期 develop/release 分支。确需维护版本时再设计发布分支。

- 分支建议为 feat/<任务标识>-<简述>、fix/<任务标识>-<简述>、docs/<任务标识>-<简述>、chore/<任务标识>-<简述>；任务标识来自现有记录，不造重复任务体系。
- 开始前核对工作区、分支、目标基线及未提交修改。用户或其他任务的修改不得随意暂存、覆盖、清理或提交。
- 一个分支对应一个可独立审阅的行为或目的；大模块按可集成增量拆分，避免每个函数都建 MR，也避免整个引擎一次合并。
- 按用户最新要求使用单一本地工作区，不创建多个 worktree。开发、测试、独立审查按固定输入串行交接，同一时间只允许一个执行者修改代码或操作分支/索引/提交；不因此自动启动额外 Agent。
- 主分支通过 MR 更新；不默认直接 push 主分支、force push、重写共享历史或删除其他任务分支。确有需要时依据实际授权与保护规则处理。

## 2. Commit

完成有意义的实现步骤后提交，暂存明确范围并核对差异。开发中的不完整提交可以保留在任务分支，不能因此绕过 MR 就绪条件。

依上述补充方案，普通中间提交也要通过适用 Commit gate；不完整指功能尚未全部完成，不是允许绕过提交前检查。实验 checkpoint 的专门保存策略另定，不以 --no-verify 默认豁免。

建议标题格式为 type(scope): 行为变化，类型为 feat/fix/refactor/test/docs/build/chore；scope 使用真实模块或省略。中文说明允许使用，不强制每个内部中间提交完全满足同一标题格式；合并后的主分支提交保持可检索。

提交说明解释问题、变化及必要取舍，关联任务。不能仅写“修改”“修复问题”。不混入无关格式化、缓存、机器私有路径、凭据或未计划生成物；必须交付的生成资产按实际资产策略处理，不一概禁止所有生成文件。

提交时检查索引中的实际内容，不能用 git add . 无差别收录共享工作区。提交身份如实配置，不冒用他人身份，也不把提交作者身份当作独立审查证明。

## 3. MR 与证据

MR 使用 [模板](../archive/2026-10-19/templates/11-MR说明.md)，至少说明问题与最终行为、任务/有效方案、变更范围、验证结果、已知限制及适用回退。简单文档修正可精简，不能省略实际未验证项。

实现未完成、检查未完成或仍有阻塞项时保持 Draft/未就绪，允许先创建 MR 展示进展；不能仅凭描述写“已验证”就进入可合并。

提交代码关联不可变源码标识；未提交测试结果用补丁标识记录，提交后确认内容对应。平台变基、squash 或合并提交改变标识时建立对应关系，不伪造旧记录为在新提交上运行过。

日志和图像等大附件保存在受控证据位置，MR 提供索引与必要摘要。不得无意公开私有资源或上传所有日志到外部服务；远程平台、可见性和证据存储在基础建设中确定。

## 4. AI 独立审查

实现者完成自检后，由独立审查上下文直接读取需求、方案、实际差异、相关调用方及证据。不能只阅读实现者总结。独立上下文可以由后续受控工作流提供，不要求不同模型；同模型的共同盲点仍需测试与边界检查补足。

审查按 [审查记录模板](../archive/2026-10-19/templates/08-审查记录.md) 记录对象版本、目标基线、范围、方法和限制，重点检查：

- 行为与范围是否符合已确认文档，是否增加无当前需求的抽象。
- 所有权、GPU 生命周期、线程/同步与失败路径是否闭合。
- 数据布局、Shader 接口、资产输入和平台能力条件是否正确。
- 测试能否识别目标错误，数值/图像预期是否有依据。
- 是否通过更改基准、规则或检查方式掩盖自身失败。

问题分阻塞、必须修复、建议。前两类处理并复核后才可通过；建议不自动阻塞。必须修复项给出实际影响、位置或规则依据，偏好不能包装成正确性缺陷。无依据的争议通过具体反例、实验或方案澄清处理，不无限投票循环。

实现者负责修复，审查者核对修复与新风险。没有独立审查条件时记录未完成，不能把同一上下文自检改名为独立审查。平台要求不同账户批准时落实合适身份与权限，不用自填批准文件绕过平台限制；具体部署能力仍待验证。

## 5. 可合并条件与版本有效性

同时满足以下条件才进入可合并：

1. 已确认需求/方案覆盖本次变化；没有待确认的基线变更。
2. MR 当前源码的必需检查通过，适用检查无缺证据；不适用项有依据。
3. 独立审查对当前变更有效，阻塞和必须修复项清零。
4. 与目标分支可集成，检查覆盖将要合并的内容及目标环境。
5. 平台保护要求满足，描述、文档和必要证据已同步。

新提交使受影响检查与审查失效，必须重新核对；无关证据可说明适用性后复用，不能机械全丢弃，也不能一概保留旧批准。目标分支变化按影响重验，必要时使用平台合并队列/合并结果检查；不能先验旧版本再趁目标变化合并新结果。

合并执行器核对源提交、目标提交、有效检查和审查对象；核对后状态变化则重新判断，不用“刚刚还是绿的”替代版本绑定。

## 6. 合并策略与集成验收

建议首版使用 squash merge，让主分支一个提交对应一个可审阅增量；保留 MR、源提交与证据对应。可回退性取决于变更内容与兼容性，不能仅因一个提交就承诺无损回退。

普通代码冲突在已确认契约内由 AI 解决并执行受影响检查/复审；冲突暴露需求、接口或架构不一致时，准备具体方案差异由用户审阅，不能自行选一边覆盖。

合并后对实际主分支提交执行适用集成检查。状态保持“已合并待集成验证”，通过后再按工作流同步规格/归档并关闭任务；不能只因 MR 显示 merged 宣称功能完成。归档收尾引用原任务，避免循环产生归档 MR。

集成失败时保留证据，停止依赖失败结果的后续工作，按既有方案修复或提交 revert；不 reset/force push 重写主分支历史。涉及数据迁移、资产格式或不可逆副作用时按专门恢复方案处理。恢复通过前不报告完成。

## 7. AI 自主权限与用户边界

| 情况 | 默认处理 |
| --- | --- |
| 已确认方案内的实现、自检、分支提交、MR、修复、满足门槛后的合并 | 按原有授权由 AI 自主执行，无逐次人工批准 |
| 改需求/范围、关键架构、契约、技术路线或降低质量门槛 | 提交具体文档差异与证据，由用户确认受影响基线 |
| CI/检查器本身错误 | 独立说明根因与修复，保留原失败；不能由受益实现任务自行放宽规则 |
| 平台保护或权限阻止动作 | 报告具体缺项，不能绕过保护或冒用身份；独立工作可继续 |

平台与归属/可见性已确定为个人 GitHub 公开仓库，origin 指向用户指定的 weimo1/AR-Engine。AI 审查结果发布、合并身份、保护配置及 CI runner 仍待建设；配置 SSH 不等于所有发布与保护权限已验证，也不授权向其他仓库发布。
