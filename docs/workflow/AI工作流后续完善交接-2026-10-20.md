## 推荐执行顺序

1. 先检查 Git 暂存区与工作区差异，保留本轮新文档和旧暂存内容；不要 reset、覆盖文件、删除旧报告或无差别 `git add --all`。同一工作区的文档修改、Git 和验证串行，不让两个对话同时写。
2. 执行无需模型的检查。下列 ci 不调用审查 API；不会证明远程保护或引擎已通过：

```powershell
python scripts/workflow.py check
python scripts/workflow.py ci
```

3. 根据发现先修复并验证，再明确实际交付范围并暂存对应文件。恢复任务的输入核对不能替代把新文档纳入暂存树：

```powershell
python scripts/workflow.py resume complete-local-workflow
python scripts/workflow.py verify complete-local-workflow
```

4. 从任务记录或 verify 输出取得当前 packet 的完整目录，再执行：

```powershell
python scripts/workflow.py review-plan '<current-packet-directory>'
```

review-plan 参数是 packet 路径，不能照旧停止交接的简写传 change-id。先检查 scope 是否确实是本次待交付输入；若任务仍为 staged，新工作区文档未暂存就不在其验证范围。

5. 向用户说明具体发现、剩余修复、预计范围与已有缓存，再决定授权范围内的实际审查。历史预算不是必须花完的额度。完整通过以后，按接入指南核验 gate，再推进发布、服务器配置和 PR 阻断试验。

日常功能开发沿用现有工具与服务端审查，不默认本地、服务器各付费审一次；首轮基线检查和后续差异审查区分。审查策略升级走已定义的可信准入，不能让候选 PR 修改自己的审查规则后自我批准。
