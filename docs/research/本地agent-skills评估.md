## 3. 最有价值的参考内容

### C++ 工程与资源管理

`cpp-oop-style` 中的强类型、明确所有权、RAII、边界校验、错误与结果表达、target 级构建配置、依赖版本治理和调试入口，适合作为工程规范的讨论素材。

其中 `references/decoupled-modules.md` 与 `references/debug-harnesses.md` 对本项目尤其相关：纯计算和真实环境交互分开，开发入口调用正式实现，通过参数、文件或受控接口调节输入，并输出可观察结果。这能支持 AI 加载场景、改变设置、截图和复现问题。

参考中的 C 句柄 RAII 范式不能直接视为 Vulkan 资源方案：GPU 在途使用、父对象、设备及分配器依赖和安全销毁时机必须单独设计。析构时拥有 C++ 对象，不自动意味着可以立即销毁底层 GPU 对象。

### 性能与正确性证据

`cpp-hpc-optimization` 要求先定义负载和误差契约，再定位热点、比较算法、建立参考实现和测量优化收益。适合 CPU 剔除、场景遍历、资产处理等热点；部分加速器材料涉及 CUDA，不能直接当作 Vulkan 实现指南。

其安装清单声明硬依赖 `cpp-oop-style`，正文也要求在控制侧使用该风格。后续若采用本项目的优化技能，需要显式改为引用已确认工程规范，不能因启用优化技能自动接受另一套架构偏好。

### Rules 与 Review

`writing-prompt` 的简短入口、明确触发条件和按需读取参考，适合现有 rules 设计。项目关键决策和长期规则必须保留，不能为了减少字数删除验收与失败处理。

`system-software-audit` 可补充资源加载、保存、异步任务、队列、退出和内存管理的审查。按真实风险选择维度，不对所有低风险修改执行完整系统审计。

## 4. 必须裁剪或适配的内容

1. `cpp-oop-style` 强调抽象接口、数据类型、值/资源类型三分法、虚接口与实现隐藏；也明确允许热点使用平坦数据和静态分发，不能简单归结为“所有代码必须 OOP”。但默认倾向仍较强，架构选择必须以需求、边界和证据决定。
2. `struct` 与 `class`、East const、成员命名、布尔运算符拼写、函数长度等是具体风格偏好，尚未成为本项目规则。
3. GCC/Clang 参数、libstdc++ 调试宏、GDB、Bash 和 Xvfb 等内容需按实际 Windows 工具链替换，不能原样运行。
4. `fresh-arch` 的重新推导思路不能覆盖已确认的兼容性、迁移和架构边界；新方案仍要先写文档交用户审阅。
5. 源仓库 `AGENTS.md` 中的命令偏好、委派阈值和确认流程只作为被评估材料，不直接复制为当前项目权限或执行规则。
6. 这些技能没有构成本项目所需的完整 SDD、TDD、MR、CI、自动合并和证据状态机；它们补充既定 OpenSpec + Harness，不替代总工作流。

## 5. 建议采用方式

先选取条款，映射到项目规范的规则 ID，并记录来源、适用范围、冲突处理和检查方式。用户确认工程与架构选择后，再决定是否需要包装成项目技能及其加载入口。

默认候选：C++ 工程参考、性能优化、按风险审计、rules 编写。按需候选：视觉检查、桌面交互与测试隔离、架构重审和方案问答。工具技能等发现实际能力缺口后再引入。

固定被采用的版本，不使用自动跟随外部仓库更新的全局规则链接。源仓库根 LICENSE 及 HPC 正文标注 `CC BY-NC-SA 4.0`；后续复制、改编或分发前应单独确认来源与适用许可，本轮只记录评估结果，不复制技能正文或示例进入引擎。

项目关键能力优先放项目级，随代码固定版本：经裁剪的 C++ 工程指导、性能优化、系统审计、引擎/编辑器视觉检查和后续验证流程。用户级仅放跨项目一致、与本引擎策略无关的通用能力，例如个人认可的提示词编写或通用调研辅助。

- 用户级：`C:\Users\未末\.agents\skills\<name>\SKILL.md`。

这是后续部署建议，不表示目录已经创建或技能已经被当前客户端发现；实施时核验实际安装版本与客户端发现结果。当前由系统、插件或其他既有位置提供的技能不在本轮迁移范围。

外部原版保持作为参考源；项目采用版需裁剪、改用清晰的项目名称，并记录来源版本和项目差异。不要用会随外部仓库更新的链接自动改变本项目规则。官方说明同名技能不会自动合并，因此不以同名用户级/项目级副本实现覆盖。

### 自动选用与流程调用

官方支持按 `description` 匹配任务的隐式调用，不要求用户每次点名；可选 `agents/openai.yaml` 中的 `policy.allow_implicit_invocation` 控制此行为，默认允许。描述需准确写出触发条件、范围与不适用情况。

自动匹配不是必经关卡。对本项目明确要求的步骤，采用“项目入口路由 + Harness 调用 + 证据核验”：入口说明何时读取何种技能；协调器在对应任务中指定适用技能与固定版本；执行器保存产出；合并检查核验产出与版本是否适用。若未安装、未发现或缺少工具依赖，报告缺口，不假装已执行。

| 条件 | 建议调用 | 是否由用户每次点名 |
| --- | --- | --- |
| 编写或审查 C++ 代码 | 项目采用版 C++ 工程指导，引用唯一工程规范 | 否，项目入口规定加载 |
| 定位性能瓶颈或修改热点 | 项目采用版性能技能与适用测量计划 | 否，按任务类型触发 |
| 资源生命周期、同步、状态机等高风险改动 | 项目采用版系统审计 | 否，由风险分类决定 |
| 编辑器布局、交互或可见输出变化 | 视觉/交互检查技能 | 否，按影响触发 |
| 编写 AI rules 与流程提示 | 通用或项目采用版 writing-prompt | 否，允许自动匹配 |
| 普通低风险文档调整 | 对应文档规则 | 不强制加载全套 C++ 和 GPU 技能 |

对于仅由特定受控阶段调用的流程技能，可以关闭隐式触发，由 Harness 在合法状态显式调用；该设置不能替代权限限制、阶段检查或保护分支。普通帮助性技能允许隐式触发，减少用户操作。

### Rules、技能与强制检查的职责

- 工程规范保存权威的编码与工程要求。
- `AGENTS.md` 规划为简短项目入口，引用文档并规定按任务加载技能；细则不全部挤进入口。
- Skill 保存某类任务的执行方法、参考资料与可选脚本，不得自行改写已确认架构或验收。
- CI、Harness 和仓库权限落实可判定关卡；读取了 Skill 或写了执行声明都不等于检查通过。

[OpenAI 官方 AGENTS.md 文档](https://learn.chatgpt.com/docs/agent-configuration/agents-md) 描述了入口发现与分层指导机制。实际会话更新与模块规则加载仍需在部署时验证，不能假设任意 `rules/` 文件夹都会自动加载。

本阶段仅记录建议。后续先确认采用条款与触发规则，再创建项目技能和入口，分别测试应该触发、不应触发、依赖缺失和版本失效的情况；最后通过一项真实变更验证流程。
