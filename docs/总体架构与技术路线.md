## 3. 总体架构目标

1. 渲染核心独立运行，编辑器可替换为示例或验证程序。
2. 两种绑定方式改变资源访问适配，不复制 PBR、阴影和场景加载逻辑。
3. CPU 场景、每帧输入、GPU 常驻资源和临时资源分别有所有者。
4. 先维护一条清晰执行路径，再按证据增加线程、队列和缓存复杂度。
5. 增加效果有明确入口，定位错误能追溯场景、Shader、资源和 GPU 提交。

第一版不建设完整游戏引擎、插件热加载、跨工具链 ABI、多图形 API 或复杂资产数据库。

## 5. 类型、资源与生命周期

核心类型为接口设计候选，命名遵守项目规范：

- `AssetId`：稳定的资产身份，不等于 ECS Entity 或 GPU 索引。
- `TextureHandle`、`BufferHandle`：建议采用类型化槽位与 generation，拒绝陈旧 CPU 引用。
- `RenderSceneInput`：当前帧对象、相机、灯光等只读值数据及受控资源引用，不保存指向可变 ECS 容器的裸指针。
- `GpuScene`：render 所有的对象、几何和材质 GPU 数据及 dirty 更新记录。
- `FrameContext`：rhi 所有的当前 CPU/GPU 帧资源和提交状态，不与交换链 image index 混为同一概念。
- `BindingMode`：SetBindless / DescriptorHeap，启动时明确选择并输出能力检查结果。
- `UploadTicket`、`SubmissionToken`：区分上传已接受、GPU 使用就绪与已完成，具体字段在模块方案中确定。

| 数据或资源 | 所有者 | 使用条件 | 回收条件 |
| --- | --- | --- | --- |
| CPU 场景 | scene | 初期主线程修改与提取 | 提取借用结束，异步引用已处理 |
| 解码数据 | assets / 显式转交的上传请求 | 上传复制前保持有效 | 数据已复制到引擎拥有的 staging 或不再需要 |
| staging 与命令池 | rhi 的上传或帧上下文 | 只由其约定线程操作 | 关联 GPU 工作完成 |
| GPU 资产和材质表 | render 持有 rhi 句柄 | 上传与状态转换已完成或由 GPU 等待正确连接 | 不再被新帧引用，所有旧引用完成 |
| 描述符槽位 | 绑定实现 | 槽位初始化且资源有效 | 引用该槽位的所有提交完成，之后才可复用 |
| 帧内临时资源 | FrameContext | 当前帧提交范围 | 完成值达到后重置 |
| 时序历史、持久输出 | render | 明确跨帧读写与重建条件 | 最后一次 GPU 使用完成后销毁 |

CPU generation 检查不能阻止已经提交的 Shader 使用旧索引；GPU 在途保护和描述符退役需要独立协议。RAII 释放的是 CPU 所有权，可以将真正 Vulkan 销毁排入退役队列。

```mermaid
stateDiagram-v2
  [*] --> CpuReady: 解码完成
  CpuReady --> UploadQueued: 请求上传
  UploadQueued --> GpuPending: 记录并提交
  GpuPending --> Ready: 满足上传与访问依赖
  Ready --> Retiring: 不接受新引用
  GpuPending --> Retiring: 取消或资产失效
  Retiring --> Released: 所有关联提交完成
  Released --> [*]
  CpuReady --> Released: 提交前取消
  UploadQueued --> Released: 确认尚未提交后取消
```

图 L1：示意单项 GPU 资产的生命周期；真实实现需补齐失败、设备丢失、取消竞态和共享资产引用规则。Ready 可以通过提交间 GPU 等待建立，不要求每次 CPU 阻塞回读。

## 6. 帧循环与线程路线

2026-10-24已确认支持worker并行命令录制，保留串行参考执行；按较粗任务拆分，实际并行粒度通过测量确定。命令池及临时分配区按帧上下文、录制worker和所需队列族隔离。交换链期望3张图像，按设备/呈现约束记录实际数量；在途帧上下文以2为默认候选，支持对照测试3。worker数、交换链图像数、在途帧数与GI历史数量分别管理。独立渲染线程、GPU多队列及具体同步原语仍待方案，不由支持并行录制自动推定。

单线程起步不表示每帧等待 GPU 空闲；允许多个 GPU 帧在途，只有复用对应上下文时等待必要完成条件。主线程/渲染线程分离时使用有界快照交接与背压，不同时引入多队列和并行命令录制。

```mermaid
sequenceDiagram
  participant Host as runtime / 主线程
  participant Scene as scene
  participant Render as render
  participant Rhi as rhi
  participant GPU as GPU
  Host->>Scene: 更新输入、层级与变换
  Host->>Render: runtime提取并交接渲染输入
  Render->>Rhi: 获取可复用 FrameContext
  Rhi->>GPU: 必要时等待该上下文上次使用完成
  Render->>Rhi: 上传、状态转换与渲染命令
  Rhi->>GPU: acquire 依赖连接后提交
  Rhi-->>Render: 返回提交标识
  Rhi->>GPU: present，等待渲染结束信号
  Host->>Rhi: 查询完成状态与回收
  Rhi->>Rhi: 回收已完成 staging、旧资源及槽位
```

图 S1：逻辑协作时序，不预设已建立独立 render CPU 线程。提交返回不等于 GPU 完成；WSI acquire/present 信号量的消费及交换链重建另有生命周期要求，不能只用图形提交完成值推断呈现资源可销毁。

任务系统先满足异步读盘、纹理解码和可独立计算的准备任务。推荐固定大小 worker 池与明确完成队列；是否使用第三方实现通过 Jobs 模块方案决定，不为“必须 Jobs”先引入完整工作窃取调度器。

CPU 内存先使用标准容器、预留容量和有限帧内 arena；只有测量证实分配热点后再评估专用分配器。VMA 只管理 Vulkan 内存。

## 7. 渲染流程与 Render Graph

建议的基础顺序：

```mermaid
flowchart LR
  Input["渲染输入与资源就绪"] --> Visible["GPU可见性与间接参数 / CPU参考"]
  Visible --> Shadow["方向光阴影"]
  Shadow --> GBuffer["不透明与裁剪材质 GBuffer"]
  GBuffer --> Lighting["延迟 PBR 与 IBL"]
  Lighting --> Sky["天空与基础透明前向阶段"]
  Sky --> Output["HDR 曝光与色调映射"]
  Output --> Ui["视口显示、UI 或截图输出"]
```

图 D1：逻辑执行顺序；具体读写依赖在 pass 方案中展开。IBL 预计算是资产准备，不要求每帧重新生成。阴影和 GBuffer 并不是所有资源都存在直接数据依赖。

建议 GBuffer 先保存可验证的法线、基础颜色和材质参数，由深度重建位置；不提前过度压缩。HDR 中间颜色使用适合的浮点格式。最终通道、格式、精度与带宽预算在基础渲染方案中确定，不能将示意表当作已确认布局。

主视图继续遵守已有 Reverse-Z、坐标和颜色规范；阴影深度单独设计，不把 Reverse-Z 主视图规则无条件复制到所有用途。暂不推翻已有旋转和投影约定，四元数存储仍是待讨论建议。

Render Graph已确认分两步接入（详细边界见2026-10-26记录C3）：

1. 最小绘制原型使用显式pass顺序，验证Dynamic Rendering、提交与资源生命周期。
2. 扩展多视图、阴影和GI前接入轻量Graph：声明资源用途、子资源范围和Bindless访问集合，检查依赖并规划同步、录制和执行。持久资源由所属功能管理。别名和自动多队列调度后续评估。

初期将 Image 按整资源追踪时要明确其保守限制。加入 Mip 生成、IBL 预滤波与 Hi-Z 等不同子资源访问前，应显式追踪 mip/layer/aspect，或在受控专用 pass 内处理并声明最终状态；不能声称简单整图追踪已覆盖任意子资源。

资源别名及自动异步Compute/多队列调度按后续测量评估；worker并行录制已纳入架构，具体粒度待验证。Shader 使用 Bindless 并不使资源依赖消失，pass 仍需要声明实际读写范围或可验证的保守集合。

## 8. 两条资源绑定与 GPU 驱动

资源绑定接口按“注册资源、生成 Shader 引用、绑定当前 pass、退役资源、输出诊断”组织；不对每个对象生成虚类，初期用两个具体实现和单次模式选择即可。固定虚接口或 variant 的具体选择留给 RHI 方案。

A：Descriptor Set + Descriptor Indexing。先实现纹理和 sampler 数组、材质索引、容量和生命周期，再学习在途更新。

B：VK_EXT_descriptor_heap。先用 set/binding Shader 到 Heap 的映射复用着色逻辑，再评估原生 GLSL Heap 访问。正确区分写入大小、槽位步长、对齐、保留区、独立 sampler 和 combined sampler 映射。

两者的 Pipeline、Shader 编译元数据与参数传递可以不同；公共材质公式和资产语义保持一致。启动时选择，首版不在运行中热切整个绑定模型。

UI backend 若保留传统 Descriptor Set，则单独安排 UI 阶段，并在跨绑定模型处完整恢复状态。不能宣称 UI 也已经采用 Heap。

2026-10-24用户明确GPU Driven为核心方向，调整“完成两条绑定后才加入”的旧顺序；基础闭环应前移，具体里程碑归属仍待重排。P6扩展/四配置实验及其是否为毕设硬要求未被取消或决定：对象包围体 → Compute 剔除 → 生成间接参数/计数 → 同步 → Indirect Count 绘制。按兼容的顶点/索引布局和管线分组；Bindless 不会自动把不同 Shader 或渲染状态合成一个 draw。

比较实验为 A/B 绑定 × CPU/GPU 可见性处理四种配置，固定场景、批次和画面质量，分别记录 CPU 提交、GPU 额外成本和整体帧时间。Hi-Z、Mesh Shader、DGC 和光追不是这条基本闭环的前置条件。

## 9. Shader 工具链与数据契约

沿用 [Flower 调研](research/Flower-Shader编译与宏机制调研.md) 的结论，glslc编译入口已经选定；本轮进一步确认首版构建期并行编译GLSL、有限变体与可追溯产物，不将运行时编译、热更新与完整反射作为前置条件。确认来源见2026-10-26记录C4，具体工具版本和元数据格式仍待验证。

Shader 编译请求包含源码、stage、入口、规范化宏、绑定模式、目标环境和诊断/优化配置。允许像 Flower 一样一个 GLSL 文件包含多 stage/pass，但每个合法变体产生独立 SPIR-V，不能用每帧宏变化代替 GPU 参数。

缓存覆盖传递 include 内容、宏、编译器、目标及选项；区分 C++ 配置和 Shader 配置。失败保留完整诊断并返回非零状态，不弹框无限重试。

GPU 数据独立于 ECS/序列化定义。初期显式结构配合 sizeof/alignof/offsetof 和 SPIR-V 接口核验；只有总大小为 16 倍数不足以证明布局一致。不要直接上传含 bool、指针、std::string 或容器的业务结构。

SPIRV-Reflect 可评估为接口核验工具，但其实际锁定版本对 Heap/untyped pointers 的覆盖要单独验证；缺少反射支持时可使用显式小规模元数据和数值测试，不伪造自动核验结果。

#### 跨模块及render内部边界

scene保存对象、层级、变换、相机、灯光等权威编辑数据，不保存描述符槽位；runtime内的提取适配读取scene并转换为render输入。render不访问EnTT容器或保存组件地址，持有自身渲染记录。初期同步调用；以后引入独立渲染线程前，另定数据交接、背压与借用期。

render内部区分持久渲染场景、每视图数据、GPU资产映射与跨帧缓存；这是职责划分，不要求每项建立独立模块或虚接口。RenderScene是方案名，表达场景中参与渲染的持久对象，而不是主相机可见列表。主相机、编辑器、阴影和表面捕获分别准备所需的可见性与pass；可以共享工具，不强制执行同一套完整流程。

图 ARCH-DATA-02：已确认的数据边界，箭头表示数据交接或消费，不表示线程、继承或静态链接关系。算法、物理布局和更新粒度仍待模块方案。

```mermaid
flowchart TD
    Scene[scene：权威场景数据] --> Extract[runtime：提取与变化交接]
    Extract --> Records[render：持久渲染场景]
    Records --> Views[每视图可见性与绘制数据]
    Records --> Cache[按需建立的表面与光照缓存]
    Changes[变换 / 几何 / 材质 / 灯光 / 移除变化] --> Records
    Views --> Passes[本帧pass与资源使用意图]
    Cache --> Passes
    History[每视图及效果历史] --> Passes
    Passes --> Rhi[rhi：Vulkan资源、提交与安全回收]
```

全量CPU遍历、GPU数据更新与资产上传是不同成本，不因“每帧提取”而每帧重建全部资源。可先用可验证的保守更新，再依据负载测量采用增量更新；具体容器、脏标记与同步协议未定。已有L1/S1是生命周期与帧流程建议，不能据本节认定其中所有参数已确认。

#### 虚拟几何、Surface Cache和GI的扩展边界

同一资产允许关联不同派生表示，例如普通几何、未来的几何簇、Cards或距离场；当前不设计格式、生成工具或资产管理器。几何前端产生表面信息，光照消费其语义，不把“普通顶点/索引缓冲加draw”固化为唯一几何模型。第一版传统GBuffer方向不变；可见性缓冲、材质求值方式等另行设计，不承诺未来接入无需改造。

材质求值与主视图GBuffer输出应有清晰边界，供后续表面捕获或命中点求值复用适用逻辑；具体材质体系、实例共享和支持子集延期。RenderScene保留主视图外对象的必要信息，GI不能只依赖主相机剔除结果。

区分表面属性缓存、光照缓存及每视图时序历史。缓存跨帧存活，由所属render功能持有，帧流程只安排本帧更新及依赖。消费者根据变换、几何、材质、自发光、灯光和对象生命周期变化决定失效范围；灯光变化不自动要求重新捕获全部材质属性。相机切换、分辨率变化、对象移除等对各效果历史分别处理，允许保守失效，具体策略待定。替换旧缓存或历史资源也必须满足最后GPU使用完成条件。

Nanite类几何、Lumen类GI与ReSTIR GI是研究方向，不是本轮选定实现；Cards生成、图集分页、缓存覆盖、更新预算、追踪表示与采样算法均待专项方案。rhi只在实际需要时增加加速结构或追踪能力；Vulkan1.4目标不能证明具体feature可用。

#### GPU Driven主路径与CPU职责

runtime组织场景变化与渲染输入，render维护持久GPU Scene及对象/几何/材质映射；具体存储与资产所有权仍延期。主绘制链路由GPU完成适用的可见性处理和间接参数/计数生成，后续绘制消费这些结果，正常主路径不依赖CPU回读可见列表再逐对象提交。主相机、阴影与辅助捕获的可见性需求分别处理。

先尽早贯通GPU Scene→GPU视锥剔除→间接参数/计数→间接绘制；遮挡剔除、LOD及虚拟几何按后续方案推进，不以Nanite完成为前提。Bindless不消除管线/状态分组，基础GPU Driven也不以Heap路径完成为前提。GPU生成数据后的访问依赖必须落实，不能只靠记录先后顺序。

#### Dynamic Rendering

自有图形pass以Dynamic Rendering为主，rhi落实开始/结束渲染及必要状态转换；render声明附件、清除/保留要求和资源使用意图，render内Graph拥有pass/资源依赖与barrier计划（该职责细化为R1建议，尚未经用户确认，确认前不作为实现契约）；runtime的阶段与提交协调职责细化见[R1待用户确认建议](#2026-10-27-待确认的职责澄清建议)。它减少VkRenderPass/VkFramebuffer对象管理，但不替代逻辑pass或Render Graph，不自动产生同步及布局转换，也不默认带来性能提升。

使用前查询并启用dynamicRendering feature；管线仍需要相应附件格式、采样等兼容信息。并行secondary录制须提供正确的Dynamic Rendering继承上下文；具体组合经验证后采用。第三方UI按实际backend支持情况接入，不为此默认建设第二套自有图形路径。P0仍仅能力查询，窗口、绘制与Shader管线不混入。

#### 自动Tick与受控扩展

runtime组织核心阶段：输入与应用更新→场景/世界变换更新→变化提取和稳定渲染输入交接→GPU Scene与视图/缓存任务准备→render内Graph生成依赖及录制任务计划、worker录制→rhi执行提交→处理完成通知和回收。此序列不表示runtime另行规划pass资源依赖；C3确认render内编排、rhi执行，进一步的提交协调及完成/回收所有权见R1待确认建议。具体可重叠区间与实现接口待设计。

应用回调用于相机控制、场景修改和参数调整；渲染功能通过声明资源读写的pass接入；截图与异步查询通过带请求身份的完成通知返回。输入交接后，当前消费者读取的数据保持稳定，后续修改进入下一次更新；稳定引用或帧数据的具体机制另定，不要求复制全部场景。Tick不等于每对象回调或全量上传，变化和预算决定实际工作量。

回调必须约定可修改状态、执行线程、注册及注销有效期。注销阻止新调用；已开始的调用须有结束或目标存活保障，不允许worker借回调任意修改scene。具体接口仍未确定。

#### 取消、场景切换与关闭

取消请求接受、CPU任务结束与资源退役完成分别表达。待执行任务可取消，已运行CPU任务在安全点收尾；放弃GPU结果不等于撤销已提交的GPU工作。场景切换使用请求身份或版本拒绝晚到结果，同时由所有权保证结果可释放。初期按旧场景安全退出后再启用新场景的保守顺序实现，重叠加载后续设计；不要求全局资产全部卸载。

关闭顺序：停止新Tick和请求→取消未执行任务/通知运行任务收尾→汇合CPU使用并处理未提交命令引用→满足GPU与呈现的实际完成条件→按依赖释放模块，诊断最后关闭。等待不持有完成方需要的锁。提交失败或设备丢失采用相应失败收尾，不等待不可能到达的正常完成信号。具体等待原语、设备异常及交换链清理仍需方案和验证。

#### 轻量Render Graph

Graph在render内收集pass及资源声明，校验依赖，生成执行、barrier和录制任务计划（该职责细化为R1建议，待用户确认）；rhi落实Vulkan命令，图形pass使用Dynamic Rendering。runtime与rhi的更细提交、完成及回收职责尚待用户确认，见R1；确认前正文不把R1细化当作已确认职责。声明包含访问用途和必要的mip/layer/aspect范围；Bindless仍须声明实际访问集合或可验证的保守集合。CPU录制并行关系和GPU执行依赖分别规划。

GPU Scene、Surface Cache及历史资源由所属功能持有，Graph导入并安排当前使用；跨帧状态和完成条件明确衔接，不能每帧重置成未知并忽略之前使用。首版轻量Graph聚焦资源、依赖、同步、执行与诊断，编译成本也测量，复用存储避免每帧大量小分配。最小绘制原型先显式执行，扩展多视图/阴影/GI前接入Graph。自动别名、多队列及调度优化后续评估。

#### Shader工程与CPU/GPU数据契约

沿用GLSL→glslc→SPIR-V及已选验证工具；首版构建期并行编译。共享坐标/颜色/表面/材质/光照语义，Set/Heap提供绑定适配，各pass提供执行入口。定义有限具名变体维度，显式登记允许组合并拒绝非法组合；频繁变化参数通过GPU数据传递。运行时编译与热更新另行设计。

区分逻辑变体身份（pass/阶段/宏等）和产物身份（源码、传递include内容、工具版本、目标、绑定模式、调试/优化选项等）。缓存失效与运行摘要关联实际产物，不以文件存在或时间戳代替完整内容身份。

对象、材质、灯光、剔除和间接参数使用GPU专用定义，核验字段偏移、对齐、数组步长、总大小及矩阵约定；不直接上传业务对象。共同定义来源和反射仅辅助布局核验，具体schema/生成工具尚未选择。Graph的资源声明、Shader接口及Bindless运行访问分别核对。优先用已知输入验证GPU Scene、材质、剔除及间接参数，反射通过不等于动态索引或画面正确。

静态查证仅作参考：Flower的[变体与运行时glslc调用](<F:/cpp project/flower/source/engine/graphics/shader.cpp>)；Chord的[permutation](<F:/cpp project/chord/source/shader_compiler/permutation.h>)和[CPU/HLSL共享定义](<F:/cpp project/chord/install/resource/shader/base.h>)；[Godot 4.6 ShaderRD](https://github.com/godotengine/godot/blob/4.6-stable/servers/rendering/renderer_rd/shader_rd.cpp)。不复制其语言、缓存、弹框重试或仅总大小检查作为本项目实现保证，未运行参考项目。

#### 资源句柄、视图和绑定

| 身份 | 职责 | 边界 |
| --- | --- | --- |
| AssetId | 持久资产引用 | 详细设计延期，不保存GPU槽位 |
| CPU类型化资源句柄 | 定位当前运行时资源，并以槽位/generation拒绝陈旧引用 | 位宽、容器及耗尽策略未定 |
| 资源视图与绑定引用 | 表达某资源的具体访问视图及Shader用途 | 同一资源可有不同视图；移除绑定不自动销毁整个资源 |
| 后端位置 | Set数组或Heap所需的位置/编码 | 受后端分配、在途使用和退役规则管理 |

Set/Heap共享资源与材质含义，允许GPU编码/布局不同，启动选择模式。直接保存后端位置与GPU逻辑索引间接表各有成本，按资源类别验证，不强制所有访问增加映射层；具体跨表协议仍待设计。

创建并初始化绑定，满足上传/访问依赖后方可使用。移除先停止新引用，再处理已录制未提交引用和已提交工作，满足实际最后使用完成条件后回收位置、视图和资源。CPU generation不能保护已提交Shader中的旧索引；Set/Heap在途更新分别设计验证。正常路径在接口与交接边界校验、批量维护GPU记录；明确缺失资源占位与无效/过期索引错误的区别。
