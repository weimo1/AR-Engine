## 1. 文档分类与权威来源

| 文档 | 约束什么 | 权威位置/规划位置 | 谁确认 |
| --- | --- | --- | --- |
| 产品需求与阶段范围 | 为什么做、做什么、本期不做什么 | 当前为根目录《渲染引擎需求.txt》 | 用户 |
| 总体架构 | 模块职责、依赖方向、主要数据流与生命周期 | `docs/architecture/` | AI 审查后由用户确认 |
| 工程规范 | 编码、契约、错误处理、测试、提交与检查要求 | `docs/standards/` | 初版及关键约束变更由用户确认 |
| 需求内的行为与验收 | 可观察行为、边界与验收条件，不单独建功能规格文档 | 需求或变更说明中维护，引用唯一条目 | 新增或变更语义由用户确认 |
| AI 任务规则 | 每次任务的必读输入、执行步骤、冲突与失败处理 | 未来入口索引及按范围加载的规则 | 初版及关键流程变化由用户确认 |
| 技术方案 | 某项能力的实现策略、接口、同步、验证与迁移 | 计划中为变更内 `design.md` | AI 审查后由用户确认；已覆盖任务不重复审批 |
| ADR | 重要决策与取舍，及其演进理由 | `docs/adr/` | 涉及架构或关键技术基线时由用户确认 |
| 验证计划 | 验收如何映射到可执行检查 | 计划中为变更内 `test-plan.md` | AI 审查；新增或放宽验收需用户确认 |
| 审查记录 | 对哪个版本、基于什么证据得出什么结论 | 计划中为变更内 review 文档 | 独立 AI 审查角色，不以用户批准替代 |
| 验证记录 | 实际执行事实与未验证项 | 计划中为变更内 `verification.md` 及证据存储 | AI 执行并由审查角色核验 |

当前产品需求保留原状。产品模板用于后续显式整理，未进行迁移前不得创建第二份相互竞争的需求源。未来 OpenSpec 当前规格仅表示已接受的具体能力，不将所有愿景写成已经实现的事实。

不再要求单独维护功能规格文档；行为、边界和验收保留在需求或变更说明。OpenSpec 的 schema 需据此适配：`specs` 如仍需要，必须可追溯引用/受控派生自唯一需求来源，并检查一致性，不形成第二套独立需求审批。该适配尚未实现，不能假定默认工作流可以直接省去 specs。

本文的 `templates/` 仅存普通 Markdown 模板，尚未注册到 OpenSpec。模板里的目录与命令位置是规划，不能作为已部署的事实。

## 2. 通用元信息

需求、架构、技术方案、工程规范与 ADR 的实例至少记录：

- 文档 ID、修订号、文档状态、关联需求/变更、依据文档及其版本。
- 创建与更新日期，使用实际日期；时区按项目约定记录。
- 本次修改摘要、待决问题和需要用户确认的具体事项。
- 确认记录的引用；没有确认记录时写“无”，不能默认已确认。

日期、文件名和“最终版”字样都不是有效版本标识。初期可以使用修订号配合归档快照，后续使用 Git 提交或内容摘要核验。文档版本确认不能仅引用会变动的分支名称。

待确认字段不得留空；使用“待定：原因/影响/下一步”。不适用项写明理由，避免用“不涉及”掩盖尚未分析的内容。

## 3. 文档状态与确认范围

状态：草案 → 待用户确认 → 已确认 → 已取代。另可标记已撤回。

- 草案可讨论和修订，不构成新的实施依据。
- 待用户确认表示 AI 已完成必要分析和适用审查，可以提供具体版本供审阅。
- 已确认表示有明确确认来源，并且确认适用于记录的内容版本与范围。
- 新修订未确认前，旧基线仍有效；冲突部分暂停，独立任务可以继续。
- 不改变语义的排版、错别字和失效链接修复可免重新确认，保留修改记录。

“待确认”不是全项目冻结，也不意味着可以按草案先行实施。低风险、可逆且在已有授权范围内的调研和技术实验可以继续。

AI 从聊天记录整理确认时，记录：确认 ID、用户表达、消息定位（若可用）、对应修订/快照、确认范围、排除项。没有稳定消息定位时保留准确摘录，并如实说明；不可编造链接或时间。

用户只确认某一项时，记录局部确认，不将整份文档改成已确认。沉默、打开文件、参与讨论或“可以继续写”不构成对全部内容的确认。

确认来源可以指向文档修订的不可变内容快照，确认记录本身作为独立附加记录保存，避免写入确认记录改变文件摘要后产生循环。仅有自填“已确认”字段不构成确认来源。

## 4. 何时重新交给用户看

| 变化 | 是否需要重新确认 | 理由 |
| --- | --- | --- |
| 新增能力、扩大本期范围、改变可观察行为 | 是 | 改变产品意图 |
| 删除验收、放宽性能或图像要求 | 是 | 改变质量承诺 |
| 图形路线、关键依赖、模块边界、存储格式或生命周期策略变化 | 是 | 改变技术或架构基线 |
| 已确认方案内的局部算法实现、函数拆分、命名调整 | 通常否 | 由 AI 实现并审查；若影响契约则升级 |
| 测试工具修复、补充检查、补充日志 | 通常否 | 不改变已确认语义与约束 |
| 文档非语义修正 | 否 | 保留修订记录即可 |

判断依据是实际影响，不是文件名。即使只修改一行代码，若改变架构契约也需要更新方案并重新确认。相关文档引用受影响的新版本后，重新判断其审查与确认有效性，不机械要求所有文档重新批准。

## 5. 提请审阅的统一格式

AI 每次提交用户审阅时提供：

1. 文档链接及具体修订。
2. 本轮需要确认的有限问题；每项写明推荐方案、理由和主要代价。
3. 相比旧基线的差异、影响范围和验证依据。
4. 尚未解决的问题，以及哪些会阻止实施。

尽量以可比较的方案帮助决定，不向用户倾倒未整理的资料。AI 独立审查结论、用户确认和运行验证是不同记录，彼此不能替代。

模板说明中“必填”表示该类实例就绪前必须回答；“按影响填写”允许写明不适用理由。小缺陷可以合并需求说明、方案和计划，但信息职责与适用关卡保留。纯格式修改无需创建完整一套文档。旧 `03-功能规格.md` 仅保留写法参考，不属于必备文档。

阶段范围、总体架构和工程规范长期维护；功能级材料按变更创建；重要技术方案中的稳定决策提炼到 ADR，以引用避免重复维护。

任务清单沿用未来所选 OpenSpec 版本的 `tasks.md` 结构，并补充任务 ID、依赖、验收引用、检查入口和完成条件；无需另造一份竞争的任务清单。

## 7. 文档就绪检查

- ID、版本、关联依据、状态清楚，引用能够定位。
- 范围和非目标清楚，未夹带未经确认的新能力。
- 关键语义、接口和资源生命周期没有以“后面再说”掩盖。
- 验收可以观察，有检查办法；数值没有凭空编造。
- 待定项标明影响；影响当前实现的关键待定项未解决则不可就绪。
- 文档结论与实际代码、实验、测试状态分开记录。
- 已完成适用的 AI 审查；需要用户确认时有明确且有效的确认记录。

这些检查目前由文档审阅执行，后续再挑选可自动化项实现检查器。

## 8. 本轮讨论边界

本轮建立文档分类、确认机制草案和模板，不认定模板条款已全部获批。接下来优先讨论：哪些材料合并审阅、工程规范中哪些属于需要用户确认的关键约束，以及技术方案的粒度。随后再进入具体架构与工具基础设施建设。

## 9. 模板选型依据与本轮调整

- 架构组织参考 [arc42](https://arc42.org/overview/)，要求系统边界图、模块依赖图、关键运行时序图与职责表；GPU 相关设计补充提交、完成与资源释放关系。
- 图示采用 [C4](https://c4model.com/diagrams) 的分层表达思路，按需绘制，使用 Mermaid 保存可维护源文本；不把 C++ 模块机械等同于 C4 container。
- 技术方案参考 [Rust RFC 模板](https://github.com/rust-lang/rfcs/blob/main/0000-template.md) 的问题、示例、详细设计、备选、代价与未决问题，并加入引擎生命周期、同步、验证和回退。
- 工程规范定义工程产物要求；审查维度可参考 [Google 工程实践](https://google.github.io/eng-practices/review/reviewer/looking-for.html)，覆盖设计、功能、复杂度、测试、命名和文档等。具体 C++/Shader 策略仍待讨论。
- AI rules 定义任务执行行为和规范加载，由检查与审查验证执行；不复制另一套编码规范，不保证仅凭提示就能强制遵守。

以上为参考理念后的项目化组织，不是复制外部模板全文，也不将外部项目的全部规则作为本项目既定要求。
