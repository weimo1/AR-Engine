## 1. 范围

约束项目自行维护的 C++ 文件组织、命名、格式与头文件。第三方源码、自动生成代码保留来源规则；确需修改时保持局部一致，不机械全库改名或格式化。

语言基线仍为已确定的 C++23。异常、RTTI、资源句柄、内存分配、线程、构建系统和具体依赖另行讨论；不能从风格示例推断这些技术选择已经确定。

## 2. 目录组织约定

采用以下顶层职责；目录仅在确有内容时建立，不预先创建空模块或通用框架：

| 目录 | 职责 |
| --- | --- |
| `engine/` | 可被独立程序使用的引擎模块 |
| `editor/` | 轻量编辑器程序及编辑专用代码 |
| `examples/` | 独立渲染示例与展示入口 |
| `tests/` | 按模块或能力组织的测试与验证场景入口 |
| `shaders/` | 自有 Shader 源文件；语言与编译策略另定 |
| `assets/` | 纳入项目管理的基础与测试资产；大资产获取和许可策略另定 |
| `tools/` | 需要维护的资产、诊断等开发工具 |
| `scripts/` | 构建、检查与验证脚本 |
| `docs/` | 需求引用、架构、方案、规范与流程 |
| `third_party/` | 仅在依赖方案决定使用仓库内依赖时建立 |

模块内部使用 `include/ar/<module>/` 放公开头文件，`src/` 放实现与私有头。模块名按架构方案决定，目录约定不直接确定模块划分或构建 target 类型。

构建产物、缓存、临时截图和本机配置与源码分开，不提交到源码目录；确需发布的生成物按发布方案管理。

## 3. 命名约定

| 对象 | 规则 | 示例 |
| --- | --- | --- |
| 目录、命名空间 | 小写，复合词按需使用下划线 | `render`、`asset_tools`、`ar::render` |
| 头文件与实现文件 | 主要类型/概念使用 PascalCase，扩展名 `.h` / `.cpp` | `Texture.h`、`Texture.cpp` |
| 类型、枚举类型与枚举值 | PascalCase | `TextureDesc`、`LoadState::Ready` |
| 函数、成员函数 | camelCase | `loadScene()`、`createTexture()` |
| 参数、局部变量、公开数据字段 | camelCase | `frameIndex`、`textureWidth` |
| 私有非静态数据成员 | `m_` 加 camelCase | `m_frameIndex` |
| 命名常量，包括静态常量成员 | `k` 加 PascalCase | `kMaxFramesInFlight` |
| 必需的项目宏 | `AR_` 加大写下划线 | `AR_ASSERT`，是否提供该宏另定 |
| 可执行入口文件 | `main.cpp` | `editor/src/main.cpp` |

缩写视为单词，例如 `GpuBuffer`、`loadHdrImage()`；外部 API 的既有名称如 `VkImage` 不改写。布尔名称表达判定含义，如 `isReady`、`hasTexture`、`canReload`。

命名表达资源语义与单位；不依靠命名替代类型或契约。不要仅凭 `Manager`、`System`、`Utils` 等宽泛名称掩盖职责不明，也不为追求某个词而拆出没有独立职责的类型。

## 4. 格式约定

- 使用 4 个空格缩进，不使用 Tab 作为缩进。
- 大括号与声明或控制语句同一行；`if`、`for`、`while` 等即使单语句也使用大括号。
- 目标行宽 100 列，由固定格式化工具执行；不可合理拆分的字符串、URL 和必要数据布局按规则保留。
- 使用 `const T&`、`T*` 的拼写，指针/引用符靠类型；本条仅决定格式，不决定所有权。
- 使用 `!`、`&&`、`||` 表达布尔逻辑；混合逻辑优先级复杂时用括号澄清。
- 不写一行多个普通声明或多条语句，不压缩复杂控制流；不以固定函数行数替代职责与复杂度审查。
- 自有文本源文件使用 UTF-8，仓库统一 LF 行尾；工具必须保留中文注释与路径，不机械改写第三方文件。

## 5. 头文件与 include 约定

- 自有头文件使用 `#pragma once`，必须能够在不依赖 include 顺序或 PCH 的情况下被包含；需要编译选项或生成配置时由构建契约提供。
- 使用到外部声明时直接包含其必要头，不依赖偶然的传递 include。
- 公开头只放调用方需要的声明和定义；实现细节与私有头留在 `src/`。模板与必须可见的定义按语言规则提供，不强制移到 `.cpp`。
- 实现文件先包含对应头，再按组包含项目其他头、第三方头、标准库头；组内按确定的格式配置排序。
- 跨模块公开头使用 `<ar/module/Header.h>`；本模块私有头使用引号路径。禁止通过相对路径绕过公开边界引用其他模块的私有文件。
- 不在头文件使用 `using namespace`。前置声明仅在语义有效且确实降低依赖时使用，不手写猜测标准库或第三方内部类型声明。
- 不要求每个头文件必有一个 `.cpp`，也不要求每个小类型都独占文件；一个文件围绕一个清楚的概念组织。

## 6. 示例：只说明表达方式

```cpp
#pragma once

#include <cstdint>

namespace ar::render {

struct TextureDesc {
    std::uint32_t width = 1;
    std::uint32_t height = 1;
};

class Texture {
public:
    std::uint32_t width() const;

private:
    std::uint32_t m_width = 0;
};

} // namespace ar::render
```

示例未规定纹理实际数据结构、资源有效性、创建方式或 GPU 生命周期；这些由技术方案决定。

## 7. 检查方式与实施边界

建议使用固定版本 clang-format 与项目 `.clang-format` 执行可格式化条款，基础建设阶段先用代表性 C++23 文件验证配置。命名与头文件依赖等条款通过合适的静态检查、头文件编译检查及 Review 补充；clang-format 不能单独检查全部规则。

自有新增和修改代码必须遵守第 2—5 节的适用约定及文中例外；目录按实际内容建立，目标行宽与合理不可拆分项保持原约定，不机械扩展为新限制。工具部署前通过实现检查与 Review 执行，后续再落实配置和检查入口。本轮不安装工具、不格式化现有文件、不创建 CI。

参考：[ClangFormat 格式选项与项目配置](https://clang.llvm.org/docs/ClangFormatStyleOptions.html)。上述具体风格是已确认的项目约定，不是对 LLVM 或来源技能全部规范的采用。

## 8. 本轮确认范围

1. 顶层职责与公开/私有头文件的组织方式。
2. PascalCase 类型、camelCase 函数/变量、`m_` 私有成员及 `ar` 命名空间。
3. 4 空格、同行大括号、100 列及 `const T&` 拼写。
4. 头文件自包含、直接 include、禁止跨模块私有引用与头文件 using namespace。
