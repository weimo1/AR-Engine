## 1. 类型职责

### TYPE-01：按语义选择 struct 与 class

- `struct` 用于主要表达数据、配置、请求和结果的类型。其公开字段可以独立变化时，不为每个字段机械添加 getter/setter。
- `class` 用于维护不变量、封装资源所有权或提供需要受控操作的对象。公开操作必须保持不变量或说明失败后的合法状态。
- 小型值类型和数学类型按实际封装需求选择，不要求“有成员函数就必须 class”。
- 不把所有具体类型都强制改成抽象接口，也不以“数据导向”为由取消必要的有效性约束。

例如，`TextureDesc` 可表达请求参数；真正拥有设备资源、创建状态或销毁责任的对象需要明确封装。类型名称只是说明，不确定实际纹理设计。

### TYPE-02：复制与移动反映真实语义

- 优先使用成员自带的值语义与 RAII，避免无意义地手写特殊成员函数。
- 唯一资源所有者不得默认复制出第二个所有者。复制如代表深拷贝或引用计数，必须明确定义成本和生命周期。
- 手写析构或移动时必须审查复制/移动/赋值的完整行为。允许不可移动类型，不为统一外观强行添加移动。
- 可移动资源对象移动后不得重复释放底层资源；源对象应处于该类型明确约定的可析构状态。不能假设所有标准库移动后对象都为空。
- 移动会影响已保存地址、回调、指针或 GPU/第三方关联时，必须证明关联仍有效或禁止移动。

## 2. 接口与抽象

### API-01：接口先说明契约

公开或跨模块接口必须明确适用的输入条件、输出/错误、所有权、借用有效期、失效条件及线程限制。类型系统可以表达的部分优先由类型表达，其他部分在契约中说明。

必须区分“发起成功”“CPU 操作完成”“GPU 操作完成”等不同结果；异步函数不能仅返回一个含义不清的成功标记。

### API-02：抽象由实际边界决定

- 需要运行时替换、开放行为集合、实现隐藏或清晰的测试边界时，可以采用虚接口。
- 不因为存在模块边界就要求每个函数或类型都加 Interface/Impl；内部计算允许自由函数、具体类型、模板、枚举或 variant。
- 闭合集合与开放扩展分别评估；不统一禁止 switch，也不把尚未确定的未来后端当作必须立即实现的框架。
- 可通过基类公开析构的多态对象必须有适当的虚析构；若禁止基类销毁，则通过可访问性与明确契约落实，不能留下可误用的普通删除路径。
- 不把可复制的多态基类按值传递以造成意外切片；具体设计需核对复制约束。

### API-03：调用方式反映使用关系

| 使用关系 | 默认表达方式 | 必须补充的条件 |
| --- | --- | --- |
| 小型独立值或明确转移的值 | 按值 `T` | 成本及复制/移动语义合理 |
| 非空借用，只读/可修改 | `const T&` / `T&` | 对象在整个访问期间有效 |
| 可空借用 | `const T*` / `T*` | 空值含义与有效期明确 |
| 借用连续元素 | `std::span<const T>` / `std::span<T>` | 元素生命周期、重分配与修改限制 |
| 借用字符串内容 | `std::string_view` | 来源内容及有效期，不默认以零结尾 |
| 转移独占动态对象所有权 | `std::unique_ptr<T>` | 接收方负责后续生命周期 |
| 建立或持有真实共享所有权 | `std::shared_ptr<T>` | 需要共享所有权的理由、解除引用的条件 |

表格是默认选择，不禁止经过设计的专用句柄、池、分配器或其他容器。若函数只是临时访问对象，不为方便强制调用方提供 shared_ptr。

## 3. 所有权与借用

### OWN-01：归属可解释

- 每个资源必须能定位释放责任方。优先值成员、容器或明确的单一动态所有者；共享所有权需要真实需求，不能用于掩盖归属不清。
- 普通业务代码中的裸指针默认不拥有对象，不通过裸指针参数暗中转移释放责任。外部 API、内存设施或低层资源边界的特殊语义必须显式标注并封装。
- 不在普通业务代码中散布成对的 new/delete 或 malloc/free。低层分配器、placement construction、第三方调用等按明确边界管理，必须有配套回收与验证。
- 不把长期泄漏或“反正退出会回收”作为默认方案，尤其不能以此逃避 GPU 与运行时资源的正常退出验证。

### OWN-02：借用不自动延长生命周期

- 引用、裸指针、span、string_view 和裸 API 句柄不自动保证其目标存活。
- 保存借用、把借用交给异步任务或捕获进回调前，必须明确保证其持续有效的机制。局部同步调用安全，不表示延迟执行也安全。
- 容器重分配、删除、场景切换、资源卸载与重建是否使借用失效，必须在契约中说明。
- 不返回局部对象的引用/指针，也不把临时对象的内容视图保存到其有效期以外。

### OWN-03：共享所有权不是同步机制

- shared_ptr 只按其具体使用规则管理所有权，不能据此认为被指向对象或同一 shared_ptr 变量的任意并发读写是安全的。
- 可能形成共享引用环时，必须重定所有权方向或采用适当的非拥有引用，如 weak_ptr；非拥有关系不能凭空保证对象存在。
- 用户数据、场景、资产和 GPU 使用的生命周期可能不同，不能默认用一个引用计数同时解决全部阶段。

## 4. 资源句柄与失效

### HANDLE-01：跨重建引用明确失效行为

长期跨模块保存的资源引用，若会经历卸载、重载、槽位复用或对象移动，必须有可解释的有效性和失效检测方案，不能只假定裸地址始终稳定。

候选可以包括稳定所有者、带版本的句柄或其他引用协议；是否采用代际索引、具体位宽、资源表与回收方式由技术方案决定。

句柄契约至少说明：无效值、所属资源域、解析失败、销毁后的访问、槽位复用影响以及线程限制。CPU 句柄有效不代表 GPU 已完成访问，二者分别验证。

### HANDLE-02：低层句柄保持在明确边界

Vulkan 或第三方句柄可以在负责它们的低层模块中直接使用；其他模块优先依赖已确认的接口契约。确需公开原生句柄时，在方案中说明用途、借用期、设备归属及调用限制，不擅自承诺跨后端通用性。

## 5. CPU/GPU 资源生命周期

### GPU-LIFE-01：RAII 管理责任，不假定立即销毁安全

CPU 所有者析构、引用清零或调用 release，只能按契约触发立即或延后回收；是否能实际销毁底层对象取决于设备使用及其他生命周期条件。

技术方案必须明确：

1. 谁持有资源、谁可以取得使用权、何时禁止新的使用。
2. 已记录但未提交的命令、已提交 GPU 工作、相关描述符与资源依赖如何处理。
3. 如何观察所有相关使用已经结束，如何防止随后再次提交对失效资源的引用。
4. 谁执行实际销毁，设备、分配器及其他必需上下文如何保持有效。
5. 出错、取消、场景切换、重建和退出时如何完成同样的回收责任。

### GPU-LIFE-02：完成条件可证明

不得凭“已经过了若干帧”、CPU 函数已返回或某个与实际使用无关的信号，断言资源可以复用或销毁。

具体 fence、timeline、队列依赖与资源回收队列由方案确定；多队列设计必须覆盖全部相关使用。若使用固定帧轮转，也必须给出对相关工作完成的真实保障，不能仅靠计数推测。

不把每次释放都等待设备 idle 作为默认通用回收策略。调试、退出、重建或受控实验中的等待可以按需求使用，必须说明其范围与成本；正常路径的策略由设计和测量决定。

### GPU-LIFE-03：验证与性能分开

对相关资源路径验证重复创建/释放、切换、resize、失败清理和退出等适用场景，核对验证层输出与实际行为。性能测试采用已约定测量配置，不把关闭验证层作为正确性通过依据。

## 6. 设计图与审查检查

- 类图/核心类型图标明拥有、借用和实现关系，不依靠相同箭头暗示不同含义。
- 生命周期复杂时补状态图；CPU/GPU 异步路径补时序图，区分请求、提交、完成及实际释放。
- Review 核对归属、借用期限、复制/移动、引用环、失效访问、异步捕获、销毁条件与上下文存活。
- 单元检查、静态分析、适用的 CPU 运行诊断与实际 GPU 验证分别提供证据；不因某种工具不可用就默认其他检查已覆盖。

本轮已确认：struct/class 按职责选择；虚接口按边界采用；优先明确单一归属；借用与共享所有权分开表达；需要可解释的句柄失效；GPU 实际释放由完成条件保证。

类型与生命周期条款不决定异常策略、CPU 分配器、资源表布局、同步原语或后端抽象框架。Vulkan 内存分配采用 VMA 的选型另记 ADR，其版本、配置与封装仍需技术方案明确。
