个人渲染引擎需求

本轮需求讨论以本文件为准，原“渲染引擎项目需求与推进规范.txt”暂不作为当前需求依据。
技术路线、第三方库选择、模块实现和开发流程在需求明确后分别讨论。

已确定的技术基线
编程语言：C++23。
图形 API：Vulkan 1.4。
Windows 开发与构建环境：采用 Visual Studio 2026 的 MSVC 工具链，由用户于 2026-10-18 明确指定；具体工具集、SDK 版本与 C++23 功能组合在基础建设时验证并固定。
Vulkan 内存分配：采用 Vulkan Memory Allocator（VMA），由用户于 2026-10-18 明确选定。版本、配置与集成方案后续确定；不代表已确定 CPU 普通对象分配器。
Shader 路线：GLSL 编写并编译为 SPIR-V，采用 glslc，并配合 spirv-val、spirv-dis 检查；工具版本、目标环境与集成后续验证。
主视图深度：采用 Reverse-Z，投影、深度格式、清除和比较状态等配套细节在技术方案中明确；其他深度用途单独分析。
诊断日志后端：采用 spdlog，通过项目薄封装提供人读文本与结构化输出，并关联运行摘要、截图及适用数值/图像检查；具体版本和配置后续确定。
引擎与编辑器使用固定且一致的工具链及运行库配置，按需采用经验证支持的 C++23 特性，不使用随工具链升级变化的 latest 标准模式。
Vulkan 扩展及具体 feature 单独查询和验证；Vulkan 1.4 不等同于支持所有扩展。
2026-10-20 阶段说明：用户暂不更新显卡驱动。允许在现有设备支持范围内先做标明 Vulkan 1.3 的开发探针，学习与验证基础能力；这不是下调 Vulkan 1.4 产品目标，也不承诺维护额外产品后端。正式 1.4 运行与 Descriptor Heap 分别验收，探针成功不算最终目标完成。SDK 安装与驱动支持状态见 docs/workflow/当前决策与待办清单.md。
资源绑定计划实现两条路径：基于 Descriptor Set 与 Descriptor Indexing 的 Bindless，以及基于 VK_EXT_descriptor_heap 的 Bindless。
两条路径共用场景、资产、材质语义与主要渲染逻辑，用于学习、调试及正确性和性能对比。先完成 Descriptor Set Bindless，再完成 Descriptor Heap；后者依赖配套驱动、SDK 与原型验证。
基础构建与依赖已于 2026-10-19 确认，清单见 docs/adr/0007-基础构建与第三方依赖选型.md；具体版本与集成待验证。
历史学习目标、双路径讨论和最初构想统一归档至 docs/archive/2026-10-19/discussions/，目录见 docs/archive/README.md。当前产品范围与技术决定以本需求、项目内 ADR 及后续明确修订为准。

一、我们要做的项目

我们要做一个以实时三维渲染为核心、可以持续扩展的个人渲染引擎。

项目首先服务于图形技术研究和高质量实时画面展示。能够加载场景、配置材质和灯光、调节渲染效果，并观察画面与性能变化。

Flower Engine 是当前主要的产品形态参考：以渲染为中心，配备够用的场景与编辑工具，能够持续加入新的渲染效果。参考其功能组织和使用体验，保留我们自己的设计与实现。

毕业设计使用这个项目的第一个完整版本。先把基础渲染做完整、做稳定，再在同一个项目中持续提升画面和性能。
实现优先级：先通过独立渲染程序完成基础画面、资源绑定、调试和性能验证；编辑器逐步补齐，不作为渲染核心、Descriptor Heap 或 GPU 驱动开发的前置条件。此顺序由用户于 2026-10-19 明确。

后续是否发展成完整游戏引擎，由实际需求决定。当前不把游戏玩法、物理、网络、脚本和游戏发布系统列入目标。

二、项目应具备的核心能力

1. 独立渲染能力
引擎能够被独立程序调用，编辑器是使用引擎的工具。
渲染功能不依赖编辑器界面才能运行。
支持通过配置和场景文件启动一个渲染示例。

2. 场景与相机
能够创建、打开、保存和切换场景。
场景中能够放置模型、相机、灯光和环境对象。
支持对象的位置、旋转、缩放及基本父子关系。
支持相机移动和视角调节，能够保存常用观察位置。
场景管理服务于渲染，不扩展为完整的游戏对象行为系统。

3. 模型与资产
能够导入常见的静态三维模型、材质和纹理，第一版明确支持 glTF 静态模型。
能够加载 HDR 环境图，用于天空背景和环境照明。
资产能够重复使用，场景保存资产引用及必要参数。
加载失败能够定位原因，并提供可辨认的缺失资源提示。
后续支持更大的场景、异步加载和资源流送。

4. 材质
具备统一的 PBR 材质表现。
支持基础颜色、金属度、粗糙度、法线、自发光等常用参数和纹理。
支持不透明、裁剪材质，以及能力范围明确的基础透明材质。
能够在界面中调整材质，并立即观察结果。
后续再扩展更多材质模型和更复杂的透明表现。

5. 光照与阴影
具备直接光照和环境光照。
支持方向光、点光源和聚光灯；第一版优先完成方向光，局部光源逐步增加。
能够通过 HDR 环境提供基于图像的照明和材质反射。
支持阴影，并能调节阴影质量和相关参数。
后续增强大范围阴影、反射和动态间接光照。

6. 渲染与画面
拥有自己的延迟渲染管线，能够完整渲染材质、光照、阴影和环境。
支持 HDR 画面处理、曝光调节和色调映射。
支持分辨率与主要效果质量调节。
后续加入环境遮蔽、抗锯齿、反射、Bloom 等效果，逐步改善画面细节和稳定性。
画面效果与渲染成本可以单独观察和比较。
同一场景能够分别使用 Descriptor Set Bindless 和 Descriptor Heap 路径渲染，比较输出、资源绑定行为和性能。

7. 编辑与调节工具
提供轻量编辑器，重点服务场景查看和渲染调节。
具备渲染视口、场景树、属性面板、资产浏览、日志和性能信息。
支持视口选择对象、变换操作、材质与灯光调节、场景保存和加载。
能快速打开示例场景，切换效果并观察差异。
暂不要求完整游戏编辑器、可视化脚本、节点材质系统或复杂内容制作工具。

8. 性能与复杂场景
能够识别不需要绘制的对象，减少无效渲染工作。
随着项目发展，提高多对象、多灯光和大场景下的处理效率。
支持查看 CPU、GPU 及主要渲染阶段的耗时。
支持查看绘制数量、可见对象数量及资源使用情况。
效果质量和性能之间有可调整的选择，不以一个脱离场景的 FPS 数字代表整体性能。

9. 调试与效果比较
提供法线、深度、材质参数、阴影等必要的调试视图。
能够打开、关闭效果或切换质量，比较画面和耗时。
能够保存截图与性能数据，复现指定相机和渲染设置下的结果。
出现资源加载、着色器或渲染错误时，能获得明确的诊断信息。
后续支持自动打开场景、设置相机和参数、截图、采集数据，方便 AI 与自动化工具辅助检查。

10. 持续扩展能力
能够增加新的渲染效果，而不反复重写整个引擎。
引擎、编辑器及外部调用方之间有清晰边界。
当前以 Vulkan 为主要图形后端，保留未来增加其他图形后端的空间。
后续可以接入其他功能模块，但渲染核心保持独立。

三、第一版先做什么

第一版的目标是完成一个可以实际使用的基础渲染引擎。这个版本同时用于毕业设计展示。

使用者应当能够完成下面这件事：
通过独立渲染程序加载一个静态三维场景，移动相机，查看 PBR 材质、方向光、阴影和 HDR 环境的画面与基础性能信息。轻量编辑工具逐步补齐模型、材质和灯光调节及保存恢复操作；完整编辑器不作为渲染里程碑的前置条件。

第一版包含：
1. 独立可运行的渲染引擎，以及轻量编辑器。
2. 静态模型、纹理、PBR 材质和 HDR 环境导入。
3. 场景对象、基本层级、变换、相机和场景保存加载。
4. 基础延迟渲染、方向光、IBL、基础阴影。
5. 不透明与裁剪材质；透明材质先支持有限的基础效果。
6. HDR、曝光调节与色调映射。
7. 基础可见性剔除、CPU/GPU 耗时与绘制统计。
8. 对象选择、参数调节、必要调试视图与截图。
9. 材质展示场景、完整展示场景，以及可调整规模的性能场景。
10. Descriptor Set Bindless 和 Descriptor Heap 两条绑定路径，按顺序接入并形成可复现的比较示例。项目计划实现两条；毕设展示优先保证已验证的稳定版本。

第一版完成的判断：
能够从加载场景一直用到调节、保存、重新打开；核心画面正确，基本操作稳定，性能信息可查看，已知限制清楚。
第一版完成后保留一个固定版本用于毕设，个人项目继续发展。

第一版暂不承诺：
实时 GI、硬件光追、体积云、虚拟几何、完整 GPU 驱动、跨平台、多个图形后端，以及完整游戏引擎功能。
最小 GPU 视锥剔除与间接绘制属于项目后续研究里程碑，与“完整 GPU 驱动”区别记录；是否列为毕设硬性验收，仍随学校要求、冻结时间与交付方案明确，本次不自动追加。具体模块和技术实现提案见 docs/总体架构与技术路线.md 第 13 节。

四、第一版之后优先增强什么

以下为候选需求，还没有全部确定先后顺序。后续根据实际画面与性能问题选取。

1. 基础画面完善
增加点光源与聚光灯，改善阴影范围和质量。
增加环境遮蔽、反射、Bloom 和更完整的后处理调节。
改善透明材质、纹理过滤和复杂材质的表现。

2. 画面稳定性
改善几何边缘锯齿、反射与阴影闪烁。
支持 TAA，并处理运动、遮挡变化和相机切换时的拖影。
后续支持超分辨率，在画质与帧时间之间提供更多选择。

3. 性能和场景规模
逐步具备 GPU 驱动渲染能力，减少 CPU 逐对象提交的成本。
增加遮挡剔除、LOD 和更有效的批量绘制。
支持异步资产加载，减少大资产加载时的卡顿。
改善 CPU 工作并行与资源管理，使复杂场景下的帧时间更稳定。

4. 渲染开发体验
改善 Shader 修改、编译反馈和效果预览体验。
支持不重启程序即可更新适合热更新的 Shader 或资源。
更方便地增加、组合、关闭和调试渲染效果。
提供更完整的性能分析与自动化场景操作接口。

五、长期想做到什么

1. 自然环境
大气散射、昼夜变化、体积雾和体积云，形成较完整的室外光照环境。

2. 动态光照
实时全局光照、更可靠的反射，以及动态物体和变化光源下的间接光表现。
结合硬件光追改善选定的光照效果，并提供质量与成本选择。

3. 大规模几何
支持更高复杂度模型和更大场景。
探索虚拟几何与资源流送，降低手工管理复杂场景的成本。

4. 更高画质与效率
持续改进时序稳定性、抗锯齿、超分和复杂场景性能。
针对具体问题研究新的渲染方法，并能与已有方法比较。

5. 更广的使用方式
按实际需要增加其他图形后端和平台。
允许其他程序或未来的游戏相关模块复用渲染引擎。

长期能力是持续研究方向，不是第一版需要同时完成的功能清单。

六、对整个项目的质量要求

画面：材质、光照和颜色处理具有一致性，常见场景下没有明显的错误表现。
性能：能够定位开销；优化有实际数据依据，同时关注平均表现与偶发卡顿。
稳定性：场景切换、对象修改、窗口尺寸变化和程序退出等基本操作可靠。
可理解性：核心渲染流程清楚，代码和概念不过度包装，便于自己理解、调试和继续开发。
可扩展性：增加效果和模块有明确位置，不要求每次重新设计整个系统。
可观察性：发生问题时能通过日志、调试画面和性能信息定位原因。

七、本轮需求的边界

本轮先确认上面的产品目标和能力范围。
具体技术决定以项目内 ADR 和已确认专项规范为准；EnTT、VMA、glslc 与基础依赖已经选定。Jobs、RHI 边界、Render Graph、反射、线程及资源生命周期、Shader 工程组织等，继续在技术方案中明确。
这些技术需要支撑需求，不把实现某个框架本身当成产品功能。

毕设需要的题目表述、研究特色和论文实验，在核心需求稳定后单独整理，不反过来主导整个个人项目。
下一步先根据本需求确认第一版的取舍，再拆技术路线，最后逐项讨论具体实现。
