# 错误、异常、断言与日志规范

文档 ID：ERROR-001。修订：草案 1。日期：2026-10-18（Asia/Shanghai）。

状态：部分确认。第 8 节的诊断方向及第 9 节的 spdlog 后端选择已确认；第 1—7 节的具体错误/异常策略仍待用户确认，最终字段、库版本和配置仍待方案。工具、错误类型与日志系统尚未实现。

## 1. 按失败性质处理

| 情况 | 默认处理 | 禁止做法 |
| --- | --- | --- |
| 资源不存在、模型损坏、Shader 编译失败等预期可处理失败 | 返回带原因的结果，由上层决定提示、跳过或使用已约定替代资源 | 在底层随意退出进程，或静默替换后报告成功 |
| 没有值但不需要错误原因，如可选项未设置 | optional 或其他含义明确的可空结果 | 把资源加载失败一律压成“没有值” |
| 正常的等待、未就绪、重建或结束状态 | 显式状态，按具体 API 契约处理 | 将所有非零返回值都判为崩溃错误 |
| 内部不变量被破坏 | 断言与必要诊断；无法保持安全状态时在受控边界停止 | 吞掉问题继续访问无效对象 |
| 设备丢失、关键初始化失败、无法维持核心状态 | 向设备/程序负责人传播，停止受影响工作并尽可能诊断和清理 | 无界重试，或承诺尚未实现的自动恢复 |

是否能够恢复由实际状态与方案决定，不根据日志级别或函数所在层级猜测。

## 2. 值式错误作为常规接口默认

- 可失败且需要原因的同步接口，应当优先返回 C++23 `std::expected<T, Error>`；无返回值使用 `std::expected<void, Error>`。固定工具链需要先验证支持，不自行加入 backport 依赖。
- `std::optional<T>` 用于“没有值本身就是充分含义”的情况。已有规范允许的可空借用指针仍然有效，不统一禁止 nullptr。
- `Error` 至少提供稳定可判定的类别/错误码和必要上下文；跨 Vulkan/VMA 边界保留适用的原始 VkResult，不能只保留难以机器判断的字符串。
- 具体错误结构、存储与格式化成本通过方案决定，不要求每次成功路径都分配诊断字符串。
- 对必须处理的失败结果使用 `[[nodiscard]]` 等适用约束；调用方必须处理或明确传播，不能用无说明的丢弃压制检查。
- 不为同一层重复维护 expected、bool+日志、全局 lastError 等多套竞争错误通道。特殊批量、多结果或性能路径可采用经过设计的状态结构。

## 3. 异常策略建议

项目自有常规 Runtime API 默认使用显式错误，不以抛异常表示日常加载失败、超时或不支持。

本条不等于立即关闭编译器异常。标准库、第三方、编辑器工具等可能产生异常，需在实际调用边界分析和转换；编译选项在工具链与依赖方案中另定。

- 线程入口、C ABI/外部回调等不能允许异常任意穿越。仅在具有实际恢复/转换策略的边界捕获，转换为任务失败或程序级处理，并保存诊断。
- 不把所有函数声明为 noexcept。仅在能够履行承诺时使用；不得为了表面一致导致潜在异常直接终止程序。
- 析构和清理路径不得向外抛异常；需要报告清理问题时采用明确诊断或其他约定，不覆盖正在传播的原始故障。
- 不使用空的 catch-all 或返回成功来吞异常；内存耗尽时不假设还能分配大型字符串或日志队列完成报告。
- 本稿不引入自动设备恢复、进程崩溃上传或远程日志服务。

## 4. 断言与输入校验

- 编译期不变量使用适用的 static_assert；运行时断言保护开发者应满足的内部条件。
- 文件、模型、纹理、场景参数、外部句柄和运行环境等必须在 Release 路径校验，不能依靠可能被关闭的 assert。
- 断言表达式不得包含必要副作用，不能把资源创建或状态更新藏在 assert 中。
- 不能继续会造成错误访问的路径，仅因 Release 断言被关闭就让它通过；具体错误返回或受控停止按状态决定。
- 是否提供项目断言宏、Debug/Release 行为与调试器中断配置，在工具方案中明确，不在本轮直接写宏实现。

## 5. Vulkan 与 VMA 返回值

- 检查需要检查的 VkResult，并按被调用函数的合法结果处理；不能用一个“只要非 VK_SUCCESS 就终止”的包装器覆盖全部 API。
- 区分本来允许的等待/未就绪、交换链相关状态、内存分配失败和设备丢失。并非所有 API 都返回这些状态，应按对应函数文档枚举处理。
- VMA 分配失败保留请求大小、用途等适用上下文与返回码；未成功创建的输出不能按完整资源继续使用。
- 多步初始化失败要清理已成功取得的部分资源，同时满足已确认生命周期要求。不能因 error 路径就忽略 GPU 或父对象依赖。
- Vulkan Validation 消息归入诊断，不代替程序状态、资源安全或实际图像验证。

## 6. 日志与诊断

建议统一 Trace、Debug、Info、Warning、Error、Fatal 的语义；日志库已定为 spdlog，具体配置待方案：

| 级别 | 含义 |
| --- | --- |
| Trace/Debug | 高频细节或开发诊断，受配置与开销控制 |
| Info | 初始化、加载完成、切换等重要正常事件 |
| Warning | 已发生降级或可继续的异常情况 |
| Error | 某项操作失败，需要定位或上层处理 |
| Fatal | 核心运行无法安全继续，不表示日志函数本身随意结束进程 |

- 错误结果负责控制流，日志负责诊断，UI 负责提示；不得仅通过扫描日志字符串推断操作是否成功。
- 在负责处理故障的边界记录一次完整上下文，传播层按需补充，不在每层重复打印相同错误。
- 诊断应包含必要的模块/操作、资源或任务标识、原因及适用原始返回值；不记录凭据或不必要的个人信息。
- 不在逐对象/逐像素或其他热点无条件格式化与输出大量日志；重复错误需限流/聚合，并仍可观察到发生次数或丢弃情况。
- 异步日志的队列、满队列策略、退出清理与 fatal 情况的降级方案需明确；不能因写日志又产生死锁或无界内存增长。
- 场景加载、Shader 编译等用户可见错误，应提供可定位的反馈；保留原有可用场景或资源的行为如需承诺，必须在相应需求与方案中明确。

## 7. 验证与待确认边界

Review 与测试按影响覆盖失败输入、错误传播、重复诊断、多步失败清理、异步失败及适用的 Vulkan/VMA 错误分支。故障注入使用隔离环境，不声称所有内存耗尽和设备异常都能被确定性复现。

本轮建议确认：常规接口优先值式错误，异常保留在受控边界，断言与外部输入校验分工明确，VkResult 按函数契约分类，日志不承担隐藏控制流。

日志库已定为 spdlog；具体 Error 类型、异常编译开关、断言实现、队列大小与诊断采集方式仍待技术方案。此前 `optional`、可空指针和所有权约定继续有效，不由本稿推翻。

参考：[VkResult 官方说明](https://docs.vulkan.org/refpages/latest/refpages/source/VkResult.html)、[VMA 错误及职责说明](https://gpuopen-librariesandsdks.github.io/VulkanMemoryAllocator/html/general_considerations.html)。上述异常默认策略是本项目建议，并非声称 C++ Core Guidelines 要求全面避免异常。

## 8. AI 开发所需的诊断与证据（核心方向已确认）

用户强调 AI 视觉判断可能不可靠，日志需要支持自动定位问题。本节的四类证据关联、人读文本与 JSONL、稳定事件/错误关联以及不以日志无错误判定画面正确的方向已确认；字段清单、采集范围、最终 schema、具体配额和图像阈值继续作为技术方案建议。

### 8.1 四类证据共同工作

| 产物 | 回答的问题 | 不能单独证明 |
| --- | --- | --- |
| 结构化事件日志 | 哪次操作、哪个资源/阶段发生什么，输入与结果如何关联 | 最终画面符合预期 |
| 运行/检查摘要 | 实际执行哪些场景与验收，状态及缺口是什么 | 每个像素或所有未执行路径正确 |
| 固定条件截图及必要调试附件 | 真实输出是什么，错误集中在哪类中间结果 | 没有可用预期时自动认定正确 |
| 数值与图像检查结果 | 哪些已定义性质、误差和回归通过或失败 | 超出检查覆盖范围的全部视觉质量 |

日志没有 Error、Validation 没报错、程序正常退出、截图文件存在，都不能单独作为“渲染正确”的判据。

### 8.2 日志输出契约

建议同一事件同时支持人读文本与 AI 可解析 JSONL，字段使用稳定 ID，不要求 AI 从自然语言猜错误类别。JSONL 必须正确编码和转义，不通过拼字符串制造无效 JSON。

基础字段建议：schema_version、run_id、event_id、level、module、timestamp、单调时间/序号、thread_id、message。根据事件适用性补充 operation_id、scene_id、asset_id、frame_id、pass_id、check_id 和原始 API 返回值；不要求每条事件机械包含全部字段。

message 可改善人读体验，自动判定依赖稳定事件 ID、字段和检查结果。不同线程与异步日志的落盘顺序不自动代表因果顺序，使用操作关联与明确状态重建链路。

运行摘要保存代码与构建标识、设备/驱动、实际启用 feature、绑定路径、场景及资产版本、相机、分辨率、效果参数、Shader 变体/哈希及验证配置。日志引用这些标识即可，不每行重复整套环境。

run_id 等应能够把日志、检查结果、截图、性能样本及原始数据关联起来。文件是当前运行产生还是旧缓存，必须能判断；缓存使用记录命中来源与内容标识。

### 8.3 优先覆盖的事件

- 初始化与设备：所选设备和能力，缺失条件，VMA 初始化与分配失败等适用诊断。
- 资产与场景：加载开始/结束、引用解析、失败原因、明确的缺失资源占位行为。启用 fallback 要有事件，不能把错误资产替换后报告原资产已成功加载。
- Shader 与绑定：编译来源、工具/目标、变体、完整诊断附件、实际绑定路径，以及已实现的布局/接口核验结果。
- 渲染阶段：pass 开关、输入/输出与配置标识、适用的资源状态和检查失败。具体 pass 结构仍由架构确定。
- 生命周期：资源回收阻塞、取消、场景失效、设备错误与退出检查，不为正常逐对象行为输出无界日志。
- 截图与检查：请求、实际完成、数据范围、输出标识和失败；输出截图不等同于比较通过。

### 8.4 可自动判断的性质与图像验证

按功能选择有独立依据的检查：矩阵与深度映射、CPU/Shader 字段偏移、资源索引和绑定范围、已知输入下的数值结果、图像有限值与参考场景误差等。不是所有检查都适用于每个 pass。

Reverse-Z 的验证需覆盖投影/深度范围、清除与比较配合、遮挡关系和深度重建；不只在日志中打印“Reverse-Z enabled”。材质与颜色检查也不能只依赖参数配置正确。

参考图/参考结果需要来源和审查依据；不能把 AI 第一次生成的输出自动设为正确基线。对固定场景提供图像差异、误差或其他适用指标；容差随设备、算法和允许误差确定，不凭空设置统一通过阈值。

出现“程序通过但画面疑似错误”时，使用分阶段开关、法线/深度/材质等调试输出与局部数值检查缩小范围。GPU readback 等诊断可能影响时序和性能，只在需要时启用并记录配置。

### 8.5 自动判定与日志完整性

- 适用的强制检查失败即失败，环境或工具不足时为阻塞/未运行，不能按“没有错误日志”转为通过。
- 关键证据丢失、运行摘要缺失、产物版本不匹配时，不得使用该运行证明完成；普通 debug 采样丢弃和关键证据丢失需区分。
- 缓冲、异步队列、磁盘满、写入失败与进程崩溃时，不承诺全部日志一定保留。记录可观察的丢弃/失败，并设计不递归调用日志系统的最低限度诊断路径。
- 控制台、文件与编辑器日志面板的过滤不改变真实错误状态。自动检查消费结构化结果，不依赖编辑器是否显示某行文本。
- 文件轮转、单次运行配额、队列容量、限流与退出刷新策略需在方案中明确，禁止无界积累；性能采样优先使用有范围的数据采集，不能把每帧全部参数灌入日志。

## 9. 日志库选型（spdlog 方向已确认）

已确认方案：spdlog 作为日志后端，项目提供薄层统一事件字段、分类、上下文和输出；不自行重写通用异步日志框架。文本输出与 JSONL 输出属于项目诊断契约，不声称只引入 spdlog 就自动实现结构化验证。

| 候选 | 可用能力与参考 | 本项目判断 |
| --- | --- | --- |
| spdlog | [异步日志](https://github.com/gabime/spdlog/wiki/Asynchronous-logging)、[sink 扩展](https://github.com/gabime/spdlog/wiki/Sinks) | 推荐作为基础后端，显式配置队列、输出和关闭行为，项目层维护字段契约 |
| Quill | [JSON 输出](https://quillcpp.readthedocs.io/en/latest/json_logging.html)、[队列策略](https://quillcpp.readthedocs.io/en/latest/users-api.html) | 保留为备选；如果实际日志开销或结构化需求显示收益，再做同条件比较 |

没有本项目测量，不宣称任一库更快。后续 ADR-0007 已选 nlohmann/json 与 vcpkg；诊断是否直接复用该 JSON 库、fmt 的独立/外部接入模式和日志版本/配置仍随集成方案决定，避免重复 fmt 配置和运行库不一致。

时间安排：诊断和后端方向已确认；实施前固定库版本、编译选项、队列满策略、同步/异步范围、容量、退出与故障路径，先通过最小验证，再让所有模块依赖。本轮只记录决策，不安装库。
