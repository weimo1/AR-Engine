# ADR-0004：诊断日志采用 spdlog 后端

状态：后端与诊断方向已确认，尚未集成。日期：2026-10-18（Asia/Shanghai）。

## 背景与确认

用户强调全 AI 开发需要可靠日志，以补足视觉判断的不足。AI 提出 spdlog 后端、薄层统一事件、人读文本与 JSONL、运行摘要及截图/数值检查关联后，用户回复“可以 继续”。

本次确认覆盖上述方向；不扩展为错误处理草案第 1—7 节全部获批，也不确定最终字段 schema、JSON 库、fmt 接入模式、日志库版本或队列配置。

## 决策

以 spdlog 作为诊断日志后端，由项目薄封装统一事件 ID、错误上下文和输出接口；日志、运行摘要、截图及适用数值/图像检查通过运行标识关联。

不自写通用异步日志框架。没有 Error 日志或 Validation 报告，不能单独判定画面正确。

## 集成前需明确

- 固定 spdlog 版本、编译模式、fmt 来源与运行库一致性。
- 文本与 JSONL 输出方式、序列化、schema 及上下文传播。
- 同步/异步使用范围、队列满策略、文件轮转、配额和丢失诊断。
- 初始化、退出、磁盘失败、关键事件与最低限度故障输出。
- 通过最小运行验证结构化解析、中文/转义、并发、队列压力、退出与证据关联。

## 代价与边界

引入外部依赖及适配层，需要维护版本、配置与许可。结构化事件和验证规则仍由项目设计，不是仅引入库就自动获得。

没有本项目 benchmark，不宣称比 Quill 等候选更快；如实际需求要求更换，提交新 ADR 与证据，不同时维护无必要的两套后端。

参考：[spdlog 异步日志](https://github.com/gabime/spdlog/wiki/Asynchronous-logging)、[Sinks](https://github.com/gabime/spdlog/wiki/Sinks)。本次未安装任何日志依赖。
